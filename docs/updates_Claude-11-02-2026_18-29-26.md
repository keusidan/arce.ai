# 更新とダウンロード

現行の仕様だけを書く。**未確認**は、実機で確かめていない。

## アプリ内更新
- `UpdateService`：リリースの一覧（`/releases?per_page=50`）を読み、**自分の OS のタグ**の中で最も新しい版を選ぶ。起動時と、起動中は設定の間隔（既定 12 時間）で確認する。ダウンロードは、手動の確認では利用者が承認してから。`<ファイル>.sha256` で検証してから、インストール。
- **自動で更新する**（`autoInstallUpdate`、既定オン）：自動のチェックで新しい版を見つけたら、そのまま download → 検証 → install まで進む。手動の「確認する」は、カードの「ダウンロード」を押してから。iOS は自動では動かさない。Android は初回だけ、システムの画面で「この提供元を許可」が必要（許可前は `UpdateReady` のまま残り、許可後に「インストール」で入る）。失敗は `UpdateFailed` に理由が残り、画面に出る。
- Android は PackageInstaller（同じ署名鍵の APK だけ受け付けられる）。Windows・macOS・Linux は、展開して、アプリの終了を待ち、ファイルを入れ替えて、再起動するスクリプトを走らせる（`desktop_installer.dart`。アプリを置いたフォルダに書き込めることが条件。`C:\Program Files` のような場所では入れ替えに失敗して元の版のまま再起動する）。展開は、SHA-256 を確かめたアーカイブだけを `tar` / `ditto` に渡す。iOS はリリースページを開くだけ。macOS は、自己更新のために App Sandbox を切っている（`macos/Runner/*.entitlements`）。
- 非公開リポジトリのときは、設定の「GitHub トークン」（`Contents: read`）が要る。アセットのダウンロードは、リダイレクト先にトークンを送らないよう、手でリダイレクトを追う。トークンは端末の安全な領域に保存される。
- 起動時に、いま動いている版のダウンロードと古い版のファイルを削除する。再開に使える新しい版の `.part` は残す。デスクトップは展開完了後にアーカイブを削除する。
- 同じ署名鍵で更新すれば、モデル・DB・設定はそのまま引き継がれる。
- 更新の対象は**プラットフォームごとのタグ**（`release-<os>` の節、`release_ci`）。

## ダウンロードの部品
- `FileDownloader`（`lib/services/file_downloader.dart`）：**モデルのダウンロードと更新が共有する**部品。1 つのファイルを、範囲要求（`Range`）に答える取得元から、大きければ**複数接続**で、途中のファイルから続きを、失敗したら**自動で取り直して**埋める。完成済み・長すぎる部分ファイル・サーバーが範囲を無視（200）・416 の扱い、無通信の判定、最後まで届かなかったことの検出、別 isolate での SHA-256 もここ。
- `SegmentedDownload`：同じ大きさの部分に分け、部分ごとに別の接続で取り、各部分を `<名前>.part.seg<番号>of<個数>` に書き、最後に連結する。1 部分は 4 MB 以上（小さいファイルは分けない）。中断しても部分ごとに取れた分が残る。接続数を変えたら前の部分ファイルは捨てる。サーバーが `Range` を無視したら 1 本に戻る。**部分ファイルは、パスの文字列ではなく、ファイルの名前で見分ける**（Windows では同じフォルダが `/` でも `\` でも書ける）。
- `DownloadErrors`（`CancelToken`、取り直す失敗の判定 `isTransient`、画面に出す文 `explain`）：取り直すのは、通信の失敗とサーバーが忙しいとき（HTTP 5xx・429）だけ。404 や 403、一時停止は取り直さない。エラーの文からは、CDN の署名付き URL（数百文字）を消す。
- 設定：「ダウンロードの同時接続数」（既定 4、1〜16。1 で従来どおり）、「ダウンロードの試行回数」（既定 3）、「ダウンロードの無通信の判定」。
- モデル側（`ModelDownloader`）に残るのは、Hugging Face のどこにあるか・大きさと SHA-256 を聞くこと・チェックして置くこと。更新側に残るのは、GitHub の API からの転送先の辿り方・`.sha256` の確認・差分更新・インストール。HTTP クライアント（`http.Client`）は、モデルの取得・更新・検索・天気がそれぞれ持つ。
- 完成済みの `.part` に「続きから」の範囲要求を出して 416 で断られたときは、同じ大きさなら再取得せずチェックへ、長ければ捨てて最初から。SHA-256（数 GB）は、画面と同じスレッドではなく別 isolate で計算する。
- **背景で続ける**：モデルのダウンロードも前面サービスに載る（通知「モデルをダウンロード中」）。アプリを閉じて（最近使ったアプリから消して）止まったダウンロードは、次の起動で取れた分から自動で続ける（設定「止まったダウンロードを次の起動で続ける」、既定オン）。ダウンロード中は、モデルの隣に目印のファイル（`<モデル名>.running`）を置き、終わる・一時停止すると消す。残っていれば、閉じて止まったもの。起動時、途中までのファイルがある未完成のモデルは「再開」の状態で出す。
- **できないこと**：最近使ったアプリから**消した瞬間**、Android は画面と Flutter のエンジン（Dart のコード）を壊す。前面サービスはプロセスを残すが、ダウンロードをしている Dart のコードは止まる。消している間も進めるには、ダウンロードを Kotlin のサービスの中で行う（または Flutter のエンジンをサービスが持ち続ける）必要がある。実機で試せない環境では、起動できなくなる危険があるので入れていない。
- **未確認**：実機の速度（1 本の接続が遅い回線で、複数接続で速くなるか。接続数 1 と 8 の比較は未報告）。過去に、ブラウザなら 100 Mbps 出る回線でアプリのダウンロードが 1 Mbps ほどしか出なかった。1 本の接続そのものが遅いという仮説で複数接続にしたが、本当の原因は端末で測れていない。

## 差分更新（Android）
- **リリース側**：新しい APK を作ったあと、直近 3 つの前のリリースの APK から新しい APK への **bsdiff** のパッチを作り、同じリリースに載せる。名前は `ARCE.AI-v<新>-android.apk.from-<旧>.patch`。パッチが APK の半分より大きければ載せない。作るのに失敗しても、リリースは止めない（`continue-on-error`）。別ジョブ `patches`（`release_ci`）。
- **アプリ側**（`UpdateService._tryDelta`）：①このリリースに、今の版向けのパッチがあるか調べる（なければ全体）。②インストール済みの APK の場所を聞く（`SystemBridge.kt` の `baseApk`。分割 APK でインストールされていれば無し）。③パッチをダウンロード（複数接続・再開は同じ経路）。④今の APK にパッチを当てて、新しい APK を作る（`lib/services/bspatch.dart`、別 isolate）。⑤新しい APK の SHA-256 を、リリースの `.sha256` と比べる。**一致したときだけ**使う。一致しない・途中で失敗した・土台が違う、のどれでも、作りかけは消して、**これまでどおり全体をダウンロード**する。
- パッチの形式は BSDIFF40（`bsdiff` や Python の `bsdiff4` が作る標準の形式。bzip2 の読み取りに `archive` パッケージ）。設定：「差分だけダウンロードする」（`updateUseDelta`、既定オン）。
- 確認済み：実際の `bsdiff4` が作ったパッチを、Dart が 1 バイトも違わずに適用できる。土台が違うとき・壊れたパッチを拒否する。実際のリリースにパッチが付いていること。
- 差分更新のパッチの大きさ：`.so` をインストール時に展開する方式（`linux_environment`）のため、UI の変更で数 MB（APK は約 68 MB）。コードの変更なしなら数 KB。
- **未確認**：インストール済みの `base.apk` が、リリースの APK とバイト単位で同じか（同じでなければ SHA-256 が合わず全体を取る）。実機で `baseApk` が読めるか。大きな APK にパッチを当てるときの時間とメモリ（古い APK・新しい APK・パッチを全部メモリに載せる）。`bspatch`（壊れた差分への耐性）の点検は、していない。
- 「キャッシング（差分更新）」は、この差分更新のこと。ビルドのキャッシュは別（`release_ci`）。
