## 1. 何のアプリか・出自・ディレクトリ

端末の中だけで動くローカル AI のチャット / コーディングアシスタント。Android・iOS・Windows・macOS・Linux で同じ画面が動く Flutter 製。
推論エンジンは **Android だけ**（llama.cpp と LiteRT-LM）。他の OS は、固定のデモ応答を返す `DemoEngine` で、画面・履歴・設定・更新機能だけが動く。ローカルの推論に加えて、オンラインのモデル（OpenAI 互換のプロバイダ）も、同じ立場の「エンジン」として使える（7 章）。

出自（git の履歴で追える）：
1. `d2147bf`：Kotlin（Jetpack Compose）の Android 専用版。推論、Python/Java 実行、署名付き APK のリリースと更新まで入っていた（`claude/new-session-5wz0e3`）。
2. `50cd4a5`：別の AI が書いた zip（`ARCE.AI-source_1.zip`）を、そのまま取り込んだスナップショット。
3. `6f22301` 以降：Flutter で書き直し（`claude/great-lovelace-3lg7st`）。デザインは HTML 製の試作 APK（`ARCE_AI_MVP.apk`）と、デスクトップのモック画像に合わせた。Kotlin の `core/` は Dart に移植し、テストも移した。
4. 以降は `main` が最新（作業ブランチは利用者が指定する。通常は `main`）。上の 2 つのブランチは履歴として残してあり、どちらも `main` に含まれている。

## 2. 作業のルール（利用者の指定）

`AGENTS.md` に、壊すと困る約束がまとまっている。ここには、その背景と、AGENTS.md に載せていないものを書く。

- 返答は日本語。時刻は**日本時間**で書く（UTC のまま書いて混乱させたことがあった）。
- 略称は初出で「略称(正式名称)」。英語由来の技術用語は英単語のまま。説明には出典を付ける。
- 新しい docs のファイル名の末尾に `Claude-MM-dd-yyyy_HH-mm-ss` を付ける（既存のファイルの編集は元の名前のまま。ツールがファイル名で読むもの — `AGENTS.md`・`README.md` など — は付けない）。コードのファイルには付けない。
- PR は、頼まれるまで作らない。push するブランチは利用者が指定する（通常は `main`）。ブランチは、頼まれるまで作らない・消さない。
- コミットの末尾に、Co-Authored-By と Claude-Session の 2 行（セッションごとに指示される値）。
- 署名鍵（`*.jks`）をリポジトリに入れない（`.gitignore` 済み）。
- **すべての版を 5 つの OS で確かめる**：版を上げて push したら、Android・iOS・Windows・macOS・Linux の結果をすべて読む。赤い OS は、次のパッチ版で先に直す（Windows は 0.8.8〜0.8.15 の間、テストが Windows のパスを想定しておらず赤のまま、誰も見ていなかった）。テストは `/` をパス区切りと決めつけない。リストして得たパスが、入力したパスと同じ文字列になるとも決めつけない。
- **`main` を常に最新に**：5 つの OS で緑になった版を、リリースが終わってから `git push origin HEAD:main`（強制しない）で `main` に進める。最初の push と同時にやらない（版が上がる push が `main` にあると、リリースがもう一度始まる）。
- 5 つの OS のリリースは、それぞれ別の workflow で**並行**に動く。OS 間に `needs:` や `workflow_run` を置かない。同時実行のグループも共有しない（同じ OS の実行どうしだけ順番になる）。
- 外部から patch やコードを取ってきて当てる workflow、コミットを push する workflow は作らない（`apply-version.yml` がそれをして、毎回失敗していたので削除した）。
- 待ち合わせに固定の `sleep` を使わず、GitHub の応答で状態を確認する。
- 初期のレビューで決めた、利用者の判断：非公開・個人利用のためライセンス対応は不要（ただし GPL / AGPL の部品を同梱するときは別。15 章）、Google Play Store には出さない、EXE の生成は対象外、Termux 関連は実装しない。

## 3. 画面の仕様

- **配置**：幅 900px 以上はデスクトップ配置（左サイドバー 280px、上バー 56px）、未満はスマホ配置（上のヘッダー＋下のナビ 4 つ）。`lib/ui/shell.dart`。左上のハンバーガーが、スマホではドロワー（履歴の検索つき）を、デスクトップではサイドバーの開閉を担う。
- **ページ**：チャット、モデル管理、生成物、詳細設定、チャット履歴（`AppPage`）。
- **チャット**（0.8.18 で Claude のような文書型にした）：
  - 返信は、アイコン・名前・エージェント名・時刻・吹き出しの枠が無い。思考・ツールの表示・本文・操作ボタン（コピー・再試行・続行）を、上から幅いっぱい（最大 920px）に並べる。ユーザーの発言だけが吹き出し（右寄せ、幅は画面の 88% まで）。左右の余白は 12。
  - 歓迎画面（4 つのチップ）、思考プロセス（折りたたみ）、ツールの結果（検索はリンク付きで折りたたみ）、`ask_user` の質問カード、承認カード（設定の変更・MCP の書き込み・プロバイダの追加・**Linux 環境のコマンド**）、エラーと注意の帯。
  - 生成中は「考えています…」のカード（エージェント名は出さない）。アイコンは 5 種（基本・リング・パルス・ドット・ローテーション）から設定で選ぶ。
  - 入力欄：ファイル添付（画像と UTF-8 のテキスト。6 章）、思考・検索・分担（コーディングモード）のスイッチ、送信/停止。**モデルのボタンは無い**（モデルの管理は下のタブとヘッダーのモデル名から）。デスクトップは Enter で送信、Shift+Enter で改行。
  - **返信は Markdown として描画する**（0.9.2。`lib/core/markdown_lite.dart` が読み、`lib/ui/chat_widgets.dart` の `RichReply` が描く）：見出し（`#`〜`######`）、**太字**・*斜体*・~~取り消し線~~・`コード`（入れ子もよい）、リンク（`[文](https://…)` と、文中の http(s) のアドレス。タップでブラウザ。`javascript:` などは**リンクにしない**）、箇条書き・番号つき・タスクリスト（字下げで入れ子）、引用、区切り線、表（`|---|` の行が届いたら表。列の揃え `:--:` に対応。幅が足りなければ横にスクロールし、1 セルは最大 280）、コードブロック。読まないもの（そのまま文字で出す）：HTML、画像、脚注、LaTeX、setext 見出し（`===`）。ストリーミング中の途中の記法（閉じていない `**` や `` ` ``、表の区切り行の前）はそのまま見え、閉じたら記法になる。
  - **モデルに求める形は、普通の Markdown だけ**（`ChatMlPromptBuilder.baseSystemPrompt`）：「Markdown で書く（リスト・太字・比較には表・見出しは長い回答だけ）」「プログラムやファイルは言語つきのコードブロックに」。0.9.2 までは「太字は `**text**` で書く」とだけ書いていて、モデルが見出しや表を避けやすかった。アプリ独自の書き方をモデルに強いてはいない（独自なのは、端末のモデルが `<tool_call>` で道具を呼ぶ形（Qwen の標準）と、` thinking` の思考だけで、どちらも本文ではない）。
  - **生成中でも別のチャットへ移れる**（0.9.6）：以前は 1 つの `ChatController` を使い回していて、生成中は「新しい会話」も履歴も開けなかった（移るとその会話の状態が消えるため、止めていた）。いまは会話ごとに `ChatController` があり（`AppController` の `_Session`）、画面に出ているチャットを離れても、生成中のチャットは**裏で続けて保存まで終える**。画面は、窓口の `ChatHandle`（`lib/services/chat_handle.dart`。常に同じオブジェクトで、中身の向き先だけが変わる）を通して、表のチャットを見る。履歴の一覧には、生成中の会話に「生成中」の印が出て、タップすると裏のチャットがそのまま表に出る。前面サービスは、どれかが生成中の間は動かす。ルール：(1) **オンラインのモデルは同時にいくつでも**答えられる。「停止」はそのチャットだけに効く（共有の `CloudEngine` には cancel を送らない。送ると他のチャットの返信まで止まるため）。(2) **端末のモデルと分担（コーディングモード）は同時に 1 つのチャットだけ**（重みと KV キャッシュが 1 つのため）。使用中に別のチャットが送ると「ほかのチャットが使っています」とエラーを出す（`SessionEngine`、`ExclusiveLease`。`lib/services/session_engine.dart`）。(3) 生成中の間は、モデル（プロバイダ）の切り替えは断る。(4) 生成中のチャットの会話を削除すると、その生成を止めてから消す。(5) 「生成中」の判定は `ChatController.isRunning`（返信の途中の、エージェントを選ぶ・MCP に聞く間も含む）。`ChatState.isGenerating` だけでは、その間に裏のチャットを片付けてしまう。**未確認**：実機での、オンラインの 2 つのチャットの同時生成と、端末のモデルの排他。
  - **停止ボタンはすぐに効く**（0.9.7）：以前は、オンラインのモデルが考え込んで何も送ってこない間（思考中）、「停止」を押しても、**次のデータが届くまで**止まらなかった（届いたところで初めてキャンセルに気づく作りだったため）。直したこと：(1) `GenerateRequest.abort` / `AiRequest.abort`（停止で完了する Future）を作り、`OpenAiCompatibleProvider` は `http.AbortableRequest(abortTrigger)` で送り、停止されたら**接続を切って**「止めた」で終える（`RequestAbortedException`）。無駄なトークンを使い続けない。(2) `SessionEngine` は、停止の合図と次のデータを競わせ、先に合図が来れば待たずにストリームを閉じる。(3) 返信の準備中（エージェントを選ぶ、MCP の道具の一覧を聞く、道具を実行する）に押した停止は、以前は忘れられていた（本番のリクエストが新しく始まって、エンジンの中断の印が消えるため）。`ChatController` が `_stopRequested` を覚え、次のリクエストを送らずに「止めた」で終える。端末のモデルは、エンジンが次のトークンで気づいて止まる（長いプロンプトの評価中は少し待つことがある。**未確認**）。
  - **「実行する」を押すとアプリごと落ちる不具合の修正**（0.11.2）：承認カード（MCP の道具など）の「実行する」を押すと、アプリが強制終了した。**原因（推定。端末のログは未確認）**：`answer()` は、道具の実行の間 `_busy` を立てて通知する（→ 前面サービスの**開始**）。実行が終わると同じ処理の続きで `_busy` を戻し、メッセージを足す通知が来る（→ **停止**）。サービスが `startForeground()` を呼ぶ前に `stopService` が届き、Android が「`startForegroundService()` のあとに `startForeground()` が呼ばれなかった」として**アプリを落とす**（[Context.startForegroundService](https://developer.android.com/reference/android/content/Context#startForegroundService(android.content.Intent)) の説明：開始したサービスは `startForeground()` を呼ぶ必要がある）。普通の送信は、生成が数秒続くので起きない。**直し方（タイマーなし）**：`GenerationService` が「まだ応じていない開始の数」を持ち、その間に来た停止は**覚えておく**。サービスは `startForeground()` を呼んだあとで、覚えていた停止を実行して自分で止まる。同じ競合は、生成が一瞬で終わる場合（すぐ失敗するなど）でも起きえたので、それも直る。**未確認**：実機で「実行する」が落ちなくなること。
  - **承認カード**（0.12.5。きっかけ：「実行許可時見づらすぎ」「実行ボタンフリーズ」「許可記憶」）：道具を実行する前の確認（`ToolApprovalCard`）を作り直した。**道具**は「server · tool」で名前を出し、引数を 1 つずつ、長い値は 240 字で切って**全部で何文字か**を添え、「全文を見る（N 文字）」で開く（開くと、スクロールできる等幅の箱で全文）。**コマンド**は `$ コマンド` をそのまま、場所と最大秒数。確認する理由が分かりにくいとき（外部の結果を読んだあと）は、カードに理由が出る。ボタンは「実行する」「実行する（この道具は次から確認しない）」「やめる」。押した瞬間に**カードが消えて、画面に「ツールを実行しています」**が出る（実行に時間がかかっても、フリーズに見えない）。ボタンは 1 回だけ答える。
  - **許可記憶**（0.12.5）：「この道具は次から確認しない」を選ぶと、道具の名前（`mcp_server__tool`）が設定 `approvedTools` に入り、以後その道具は聞かない。**対象は MCP の道具だけ**（コマンドは、何をするかがコマンドで決まるので、記憶できない）。外すのは、設定 → MCP サーバー →「確認しない道具」の ✕。**チャットからは見ることも変えることもできない**（`blocked`。メッセージで確認を切られないため）。
  - **右上の設定アイコンを消した**（0.12.5）：下の 4 つのバー（スマホ）・サイドバー（デスクトップ）に「設定」があり、ヘッダーのアイコンは重複だった。
  - **途中送信**（0.12.6。きっかけ：「途中送信指示」、答え：「次の道具の区切りで割り込ませる」）：返信の最中も入力欄は使える。文を書いて **「割り込む」**（デスクトップは Enter）を押すと、文は入力欄の上に「次の区切りで伝える: …」と出て（✕で取り下げられる）、**今動いている道具は止めずに**、その道具が終わった**次の区切り**で、モデルに**別のユーザーのメッセージ**として渡る（履歴は 道具の結果 → 割り込みの文 の順。画面では、それまでの返信はそこで区切られ、新しい返信が続く）。道具を使わないまま返信が終わったときは、残っている文が**次のメッセージとして自動で送られる**（止めたときも同じ。エラーや質問で止まったときは入力欄の上に残る）。複数の文は 1 つのメッセージにまとめる。**ファイルの添付は割り込みでは送れない**（返信が終わってから）。長い分担の仕事（`delegate`）の途中では、その仕事が終わるまで割り込めない（道具の区切りだから）。実装：`ChatController.interject / unqueue`、`ChatState.queued`。
  - **通知**（0.12.6。きっかけ：「許可必要通知、完了失敗通知」。Android のみ）：返信が**許可・答えを待って止まった**とき、**終わった**とき、**失敗した**ときに、システムの通知を出す。種類ごとに設定（`notifyNeedsYou` / `notifyDone` / `notifyFailed`、既定はすべてオン）と、`notifyOnlyAway`（既定オン＝**そのチャットを画面で見ているときは出さない**。アプリが前面でも別のチャットの返信なら出す）。判定は `ReplyWatch`（返信が動いていた状態から止まったときだけ。保存した会話を開いただけ・停止・途中の段階では出さない）。設定をオンにすると、Android 13 以降は通知の許可を聞く（`NotifyBridge.kt`。画面がなくなっても通知は出せるが、許可の質問には画面が要る）。「確認・失敗」は音の出るチャンネル、「完了」は通常のチャンネル。同じ会話の通知は 1 つに置き換わる。**通知を押すとアプリが開くだけ**で、その会話までは開かない（未実装）。iOS・デスクトップは未対応（何もしない）。

  - **コードブロックの折りたたみ**（0.10.2）：見出しのタップで折りたたみ/展開（折りたたむと `python · 20行` と出る）。14 行を超える長いブロックは、下にも「折りたたむ」「コピー」が出る。設定「長いコードブロックを折りたたむ行数」（`codeFoldLines`、既定 0＝折りたたまない）で、長いブロックを最初から折りたたむ。書いている途中のブロックは、いつも開いている。
  - **返信の進み具合**（0.11.1。きっかけ：「分担をすると思考の後に消える／進んでいるのか分からない」）：返信している間、最後の返信の下に**状況の枠**（`RunStatus`）が出る。1 行目に**いまの段階**（「プランナーが考えています」「検索しています」「開発モデルが作業しています（1/3 件完了）」「プランナーが回答を書いています」など。分担のときだけ「プランナー」、ほかは「モデル」）、2 行目に**詳しい 1 行**（思考のときは、モデルが最後に書いた見出し（`**…**` や `## …`）か最後の行。検索の語。作業中のタスクの名前）、3 行目に**数字**（`2 回目の返信 · 通信 5 回（プランナー 3・開発 2） · ツール 1 回 · 1:24`。時計は 1 秒ごとに進む）。終わると**1 行の薄い字**（`通信 5 回（…） · 所要 1:24`）だけが残り、別の会話を開く・新しい会話にすると消える。数えるもの：通信＝モデルへの要求（再生成・空の返信のやり直しも 1 回。開発モデルへの要求は 1 タスクごと。フォールバックで別のモデルへ切り替わった分は数えていない）、ツール＝道具を実行した回数。実装は `lib/core/run_progress.dart`（`RunProgress`・`RunMeter`・`ThinkingHeadline`）で、`ChatState.progress` を介して画面に届く（保存はしない）。`DelegateRunner` も `RunMeter` を受け取って、開発モデルの進み具合を知らせる。
  - **思考が消える不具合の修正**（0.11.1）：道具を呼ぶたびに、思考の本文が**そのラウンドの分だけに置き換わって**いた（最初の思考が、2 回目の返信が始まると消えた）。いまは、前のラウンドの思考の後ろに続けて足す。**空の返信**（本文も道具も無く、前の道具の結果の表示も無い）は、何も出さずに終わらず、`retryLimit` 回まで同じ要求をやり直し、それでも空なら「プランナーの返信が空でした」、思考だけで出力の上限（`length`）に達したときは「最大トークンを増やすか思考を弱めてください」と**画面に出す**（再試行ボタン付き。空の返信は自動報告の対象）。道具のラウンドが終わるごとに、そこまでの返信を**履歴に保存**する（長い分担の途中でアプリが閉じられても、残る）。ただし、実際の Gemini で何が空になっていたかは未確認（空の返信か、上限か）。
  - コードブロックはコピーできる。HTML は「プレビュー」で、`PreviewServer`（127.0.0.1）経由でシステムのブラウザに表示する（サンドボックス付き）。

## 4. 中核の仕様（`lib/core`）

- **チャット制御**（`chat_controller.dart`）：1 回の返信は「エージェントを選ぶ → プロンプトを作る → エンジンから流れてくる文字を `StreamSegmenter` で思考・本文・ツール呼び出しに分ける → ツール呼び出しなら実行して続ける、`ask_user` なら質問カードを出して待つ」の繰り返し。ツール呼び出しが途中で切れたら、設定の回数だけ書き直す。最大ツール回数を超えたらエラー。**同じ道具・同じ引数が 3 回続いたら**「同じ道具を繰り返し呼んでいます」で止める。会話は返信の開始時（生成中フラグ付き）と終了時に保存する。
- **状態**（`TaskState`）：waiting / search / thinking / userWait / generation / completed / error / cancelled。遷移は `GenerationTask` が検査する。
- **エージェント**：General Chat / Coding / Research / Artifact / File Analysis。キーワードで選び、迷うときだけ（設定が有効で、モデルが読み込み済みなら）モデルに厳密な JSON で選ばせる。ユーザーが指定すればそれが最優先。5 つ全部に `get_settings` / `update_settings` / `add_provider` を許可している。
- **プロンプト**：Qwen3 の ChatML。口調は `<tone>` で囲み、制御用の文字列を取り除く（200 文字まで）。
- **ツール**：`ask_user`、`web_search`、`get_weather`（Open-Meteo）、`get_time`（`timezone` パッケージ）、`get_settings`、`update_settings`、`add_provider`、MCP のツール（`mcp_<サーバー id>__<ツール名>`）、アプリ自身の **`run_command`**（0.12.0。Linux 環境。15 章・19.5）と **`ci_status`**（0.12.0。GitHub Actions の読み取りだけ。10.5）。
  - 検索の順：SearXNG のアドレス（入れていれば）→ 登録した検索 API（一覧の順、有効なもの）→ DuckDuckGo Instant Answer。10 章。
  - 道具の定義が変わったので `Protocol.schemaVersion` は **5**（`run_command` と `ci_status` を足した）。
- **長い会話の圧縮**（0.12.7。きっかけ：「チャット圧縮」。以前は、会話が文脈に入らなくなると「新しい会話を始めてください」と断っていた）：返信のたびに、**送る前**に、リクエストが文脈の `compactAtPercent`％（既定 80）を超えそうか数える（`ChatController._makeRoom`。文脈の大きさが分かるときだけ：オンラインのモデルは設定・自動取得の値、端末のモデルは読み込んだ文脈長）。超えるときは、順に：**(1) 古い道具の結果を切り詰める**（直近の発言より前の道具の答えを `compactToolResultChars` 文字まで。長い検索結果や MCP の答えが一番かさばるため。モデルは使わない）→ 足りなければ **(2) 直近 `compactKeepTurns` 件の発言より前を、モデルに要約させる**（`Compaction`、`lib/core/compaction.dart`）。要約の依頼は、会話を「文脈の 4 割」ほどの大きさの組に分けて**組ごとに**書かせ、前の要約を次の依頼に添える（要約の依頼自体が文脈に入るように）。要約は、**残す最初の発言の頭に入れる**（「[Summary of the earlier conversation…] … [The user's message that follows the summary] …」）ので、ユーザーとアシスタントの交代は崩れない。道具の呼び出しとその答えの間では切らない（切り目は、必ずユーザーの発言の頭）。アプリが履歴に書いた注意（`[from the app]`）は「発言」に数えない。要約を書けなかったとき（エラー・空・思考だけ）は**履歴を変えず**、そのまま送る（足りなければ、いつもの「入りません」のエラー）。**画面のメッセージは消えない**（モデルに送る履歴だけが変わる）。返信に「会話の前半（N 件）を要約しました（約 A → B トークン）」と出る。**手動**：入力欄の下のトークン数の横の「会話を要約する」（`canCompact` のとき。`compactNow`。文脈の大きさに関係なく今すぐ）。設定（制限のグループ）：`compactEnabled`（既定オン）・`compactAtPercent`・`compactKeepTurns`（既定 4）・`compactSummaryChars`（既定 3000）・`compactToolResultChars`（既定 1500）。チャットからも変えられる（`AgentSettings`）。**使うモデルは、いま答えているモデルそのもの**（別のモデルを選ぶ設定はまだ無い）。端末のモデルでは、要約の依頼が KV キャッシュを一度押しのけるので、その返信は遅くなる（6.2）。**未確認**：実機の端末モデルでの要約の質（小さいモデルは下手なはず）。
- **JSON の方針**（初期のレビューからの決定）：JSON は GBNF（llama.cpp の文法）で縛る。ただし、縛るのは**構造が必要な部分（質問タイル・tool call）だけ**で、本文は Markdown のまま。決まった合図（`<tool_call>`）が出たところから文法を効かせる（lazy grammar）ので、Thinking と本文は自由に書ける。Tool と質問の定義は JSON Schema で書き、llama.cpp の変換で文法にする。形式が崩れたときは修復せず、途中切断のときだけ再生成する。意味のチェック（`options` が空でない、など）は別に行う。Schema にはバージョン番号を付ける。出典：16 章の経緯と、18 章の llama.cpp の文書。
- **モデルカタログ**：基本は Qwen3.5-0.8B（Q8_0）。Qwen3 の 0.6B〜14B（GGUF）と、LiteRT-LM の 4 種。NPU 用は、その SoC の端末にだけ出す。GGUF と `.litertlm` は形式が違うので、エンジンごとに別の一覧。
- **Kotlin 版からの違い**：Coding エージェントの説明から、Python/Java の実行とビルドの記述を外した（Flutter 版には無いため）。0.12.0 からは、シェル（`run_command`）で同じことができる（15 章）。

## 6. データの保存

### 6.1 会話の履歴：SQLite（`arce_llm.db`）

これまで 1 会話 1 ファイル（`conversations/<id>.json`）だったものを、SQLite に移した（0.4.2）。

- 層：画面（`history_page.dart`、ID は UUID の `String`）→ `conversation_database.dart`（DB を開く・旧 JSON の取り込み・`list/save/get/delete/clearGenerating/search`）→ `conversation_snapshot_store.dart`（画面のスナップショット `messages/history/nextId` を読み書き。Flutter 非依存）→ `llm_db.dart`（スキーマと DAO）。
- テーブル：`conversations`、`messages`、`parts`、`assets`、全文検索の `messages_fts`（FTS5 の `trigram`。日本語の部分一致が効く。3 文字未満は索引できないので `instr()` で補う）。WAL モード。DB は **schema 3**（`turns` に思考を持つ `reasoning` 列を足した。`ALTER TABLE` なので前の DB は思考なしで読める）。
- **決めたこと**：
  1. 保存は追記ではなく**置き換え**（`replaceMessages`）。画面は返信の開始時と終了時に会話全体を渡すので、追記だと生成中の返信が 2 行になる。メッセージ ID は位置（`<会話ID>@<seq>`）から作り、何度保存しても行が増えない。
  2. アプリが落ちた中断は `finish_reason = 'interrupted'` と書き、読み戻すときに `cancelled` にする。起動時の「続きから再開」が効くように、利用者の「停止」と見分ける。
  3. 旧 JSON の取り込みは毎起動でよい（ID が `legacy-<元の id>` なので冪等。ファイルは消さない）。
  4. モデル履歴（`turns` の user/assistant/tool）も DB に入れる。
  5. **設定・プロバイダ定義・API キーは DB に入れない**（設定 JSON と secure storage）。DB は会話データ専用。
- 保存の形式を SQLite 以外にするかを検討して、**SQLite のまま**にした：Isar（元のプロジェクトはもう積極的には開発されず fork に分かれた）、Realm（Atlas Device SDK が 2024-09 に deprecated、2025-09-30 に終了予定）、ObjectBox（検索した範囲では組み込みの全文検索が見つからず）、Hive / sembast（全文検索が無い）、専用の全文検索（Tantivy。履歴の規模では過剰）は選ばなかった。
- **巨大な塊（KV キャッシュ、モデルのファイル）はファイルに置き、索引だけを SQLite の `assets` に持つ**（`AGENTS.md` の規則）。

### 6.2 KV キャッシュ（0.8.1）

- 追加したもの：KV の型に **Q4_0**（F16 : Q8_0 : Q4_0 ＝ 64 : 34 : 18 バイト／32 値。既定は F16）。JNI の `nativeLoad` の最後の引数は `Boolean kvQ8` から `Int kvType`（0/1/2）に。量子化した V キャッシュには flash attention が要る。
- **ファイル保存**（設定「ローカルモデル → KV キャッシュをファイルに保存」。**既定はオフ**）：`llama_state_seq_save_file` / `llama_state_seq_load_file`（組み込み用の C API）を JNI から呼ぶ。保存するのは**最後のプロンプトの分だけ**（返信の分は次のプロンプトで再利用できないので捨てる）。
  - 保存先 `<アプリのデータ>/kv/<会話ID>.<指紋>.kv`。`.tmp` に書いてから rename。
  - 索引は `assets` の 1 行（`mime = application/x-llama-kv-state`）。会話を消すと行もファイルも消える。合計の上限（既定 1024 MB）を超えたら、最後に使った時刻が古い会話から消す（LRU）。行のないファイル・ファイルのない行は、保存のたびに片付ける。
  - **指紋**：モデルのファイル名・サイズ・文脈長・KV の型・アプリの版。1 つでも違うと読まない（llama.cpp の保存形式は版で変わりうる）。アプリを更新すると、保存済みは使われなくなり LRU で消える。
  - 保存するとき：会話の切り替え・新しい会話・バックグラウンドに回るとき。復元するとき：履歴から会話を開くとき（復元の直前に、利用者がもう書き始めていたら復元しない）。
  - 保存しないとき：プロンプトが短い（既定 512 トークン未満）、再帰・ハイブリッド系のモデル（Qwen3.5 など）、LiteRT-LM。
- **圧縮との両立**（0.12.7）：会話を要約で短くしたあとも、KV キャッシュは壊れない。llama.cpp は、新しいプロンプトと保存してある状態の**共通の先頭だけ**を使い、違う所からは読み直すだけだから。要約は「最初の発言の頭」に入るので、要約した直後の 1 回は先頭が変わって読み直しになるが、**その返信が終わったときの保存（会話ごとに 1 つ。古いものは置き換わる）が、要約後の履歴の分になり**、以後はまた先頭が安定して再利用される。要約の依頼そのもの（別の指示で、同じエンジンを通る）は、その場の KV を一度押しのける。
- 容量の目安：1 トークンあたり `2 × 層 × KV ヘッド × ヘッド次元 × 要素のバイト数`。Qwen3-14B 相当の F16 は 160 KiB/トークン（4096 トークンで約 640 MiB）。数百 MB になりうるので既定はオフ。
- 貼ってもらった方法のうち PagedAttention・RadixAttention・LMCache・vLLM は、サーバー向けで 1 台のスマホで llama.cpp を埋め込むこのアプリにはそのまま当てはまらない。prefix の再利用は、すでに `arce_llama.cpp` の `reuse_prefix` にある。

### 6.3 添付ファイル（画像とテキスト）

- 中身を**ファイルの先頭のバイト**で見て決める（拡張子は見ない）：画像（PNG / JPEG / GIF / WebP）、UTF-8 のテキスト（SVG・ソース・Markdown など）、それ以外は断る。画像は、画像に対応するモデルには画像として送り、対応しないモデル（端末のモデルを含む）には理由を出して断る（バイト列をテキストとして渡さない）。
- 上限は、画像が 1 枚 4 MB（Anthropic の 5 MB が最も低いため）、添付は 5 ファイルまで、テキストは 1 ファイル 8000 文字・合計 16000 文字（いずれも設定にした）。
- 「画像に対応する」は、モデルごとの設定（`ModelConfig.vision`、「画像を送る」スイッチ）。触っていないモデルは、名前から推測する（`gpt-4o`・`claude`・`gemini`・`llava`・`-vl` など。外れたらスイッチで直す）。送り方は OpenAI 互換の `image_url`（`data:` URL に base64）。
- 画像は、プロンプトの本文に目印 `<image id="…" name="…"/>` として置き、バイトは `GenerateRequest.images`（id → バイト）で別に運ぶ。id は中身の SHA-256 の先頭 16 文字。対応しないプロバイダには `[画像: ファイル名]` に置き換える。
- 制限：画像のバイトは**会話を開いている間だけ**メモリにある（開き直すと目印だけが残り `[画像: ファイル名]` として見える。保存するには `assets` とファイルへ書く必要がある）。画像は縮小しない。添付のチップは画像でもファイル名だけ。Anthropic など OpenAI 互換でない API の画像形式には未対応。

## 7. クラウドのモデル（プロバイダ）

### 7.1 構成

- `AiProvider`（`lib/ai/provider.dart`。Flutter 非依存）が、`Delta`（本文・思考・ツール呼び出し・使用量・停止理由）の流れを返す。`openai_compatible.dart` が chat-completions の SSE を読む：chunk の境界で切れた行の復元、`reasoning_content`（または `reasoning`）の分離、分割で届く関数呼び出しの引数の組み立て、`usage`、`finish_reason`。接続先ごとの差は headers / body の上書きで吸収。失敗は日本語で原因別。
- `CloudEngine implements InferenceEngine`：プロバイダを普通の推論エンジンとして扱う。`RoutingEngine` が、端末のエンジンとクラウドを要求ごとに振り分ける。`local` は予約 id（端末のモデルは、並んだプロバイダの 1 つ）。
- **決めたこと**：
  1. プロンプトは **1 本の ChatML のまま**。どちらのエンジンでも同じものを作り、クラウドに送るときだけ `ChatMlBridge` がメッセージ列に分解する。
  2. **続行**は、書けている本文を最後の assistant メッセージとして送り、「その続きから書く。繰り返さない」という user メッセージを足す（OpenAI 互換の API には prefill の口が無いため）。
  3. **API キーは設定に持たせない**（`provider_key.<id>`、実体は `flutter_secure_storage`）。設定 JSON のコピーや QR で、キーは出ない。
  4. **黙って乗り換えない**：選んだプロバイダが失敗したら、その失敗を見せる（端末で答え直さない）。画面の回答元と、実際に答えた相手がずれないように。
- **複数のプロバイダと、1 つに複数のモデル**（0.8.0）：`ProviderConfig.models`（`ModelConfig { id, name, params, prompt, … }`）と `activeModel`。前の「model 1 つだけ」の保存は、読み込み時に 1 件へ移行する。
- **ツールをクラウドへ渡す**（0.5.2）：以前は `CloudEngine` が `AiRequest.tools` を詰めておらず、プロバイダに道具の定義が一度も送られていなかった。`GenerateRequest.tools` を足して直した。`provider.capabilities.tools` が false のときは送らない。
- **思考**：クラウドは `reasoning_content` を読んで `<thinking>` として流す。モデルが返さない場合（`deepseek-chat` のような非 reasoning モデル）は出ない。端末は、速度⇔精度が 0.25 未満だと思考しない。続行の返信は思考を飛ばす。

### 7.2 モデルごとの上限と、公式の推奨（0.8.2）

きっかけ：DeepSeek V4.1 Flash が「少ししかいじらない」「指示を読めない」。調べると、最大トークンの既定が 2048（`effectiveMaxTokens` ＝ `maxTokens × (0.5 + 速度精度)`）で、思考の分で途中で切れていた。temperature / top_p も Qwen3 用の値のまま。

- `ModelConfig` に**コンテキスト長**（`contextTokens`）と**最大出力**（`maxOutputTokens`）。
- 最大トークンの決め方（強い順）：**モデルごとの設定 ＞ 設定画面でユーザーが決めた値 ＞ 公式の推奨 ＞ アプリの既定**。結果は、モデルの最大出力と、文脈に残った分（コンテキスト − 入力の見積もり − 512）に収める。temperature・top_p も同じ順。ユーザーが選んだ小さい値は下限で持ち上げない。
- **公式の推奨があるのは、モデルカードのあるバージョンだけ**：DeepSeek V4／V4.1（temperature 1.0・top_p 1.0・max_tokens ≥ 256K・文脈 1M）、GLM-5 以降（temperature 1.0・top_p 0.95・最大 64K〜128K）。それ以外は従来どおり。モデルの編集の「公式の推奨を入れる」で値が入る。`lib/ai/model_hints.dart`。
- 上限の引き上げ：モデルごとの最大トークン 131072 → 1,048,576。
- **自動取得**：①プロバイダの `GET /models`（文脈＝`context_length`・`context_window`・`max_context_length`・`max_model_len`・`inputTokenLimit`、出力＝`top_provider.max_completion_tokens`・`max_completion_tokens`・`outputTokenLimit`、画像・ツールの対応。**曖昧な `max_tokens` は読まない**）、②Hugging Face の `config.json`（モデル名が `owner/name` のとき、文脈長だけ。`max_position_embeddings`、`text_config` の中も読む。**モデル名だけ**を送る。設定でオフにできる）。いつ：使い始めたとき（モデルごとに 1 回）、プロバイダの「取得」、モデルの編集の「上限を取得」。**ユーザーが入れた値は、自動では消さない**。
- 確認の対象：DeepSeek V4.1 Flash の公式モデルカードと `encoding/README.md`、`deepseek-ai/deepseek-recipe`（既定の max_tokens は 8192／65536／131072）、GLM-5.3 の公式モデルカード。「DeepSeek Harness」は実在する公式（`deepseek-ai/deepseek-harness`、`dsh`、MIT、developer preview）だが、harness は agent を動かす側で、アプリが従うべき通信の仕様書ではない（仕様にあたるのはモデルカードの `encoding` と `deepseek-recipe`）。`HenryZ838978/deepseek-harness` は非公式の再実装、`deepseekharness.dev` など公式を名乗るサイトの数字は根拠にしない。

### 7.3 思考（推論）をプロバイダへ届ける（0.8.3）

モデルごとに**「思考の送り方」**（モデルの編集 →「思考（推論）」）。**既定は「送らない」**（提供元の既定で動く。DeepSeek も GLM も既定で思考する）。この間、チャットの思考スイッチはこのモデルに届かない（トーストで伝える）。

| 送り方 | 足す項目 |
|---|---|
| DeepSeek の API | `thinking: {type: enabled/disabled}`、思考オンなら `reasoning_effort` |
| Z.ai の API（GLM） | `thinking: {type, clear_thinking}`、思考オンなら `reasoning_effort` |
| chat template のサーバー（vLLM・SGLang・Together・DeepInfra など） | `chat_template_kwargs: {thinking, enable_thinking, thinking_mode, reasoning_effort, clear_thinking}` |
| OpenAI の形 | `reasoning_effort`（low/medium/high。max は high。オフは表せないので足さない） |
| 送らない | なし |

- 思考のオン/オフ：自動（チャットのスイッチと速度⇔精度に従う。速い側の端はオフ）／常にオン／常にオフ。推論の強さ：入れた値が先（`low`/`high`/`max` または 1〜100）、空欄はスライダーから（0.5 未満 `low`、0.85 未満 `high`、以上 `max`）。
- GLM の `clear_thinking`：GLM-5.3 のモデルカードが「チャットでは true を明示」と書いているので、GLM の「おすすめの送り方を入れる」は true を入れる。
- 「おすすめの送り方を入れる」：名前から選ぶ（`owner/name` は vLLM 系 → chat template、素の名前はメーカー自身の API）。**ボタンを押したときだけ**入る。
- 項目は、生成した項目のあと・プロバイダの「追加のリクエスト項目」より前に入る。同じ名前は、プロバイダの上書きが勝つ。
- コーディングモードの役は思考のスイッチを持たないので、「自動」を「思考オン（スライダーは中ほど）」として扱う。

### 7.4 ツールの会話の形と、思考を返す（0.8.4）

- モデルごとの**「ツールの送り方」**：自動（既定。提供元が対応していれば function calling、していなければテキスト形式）／function calling（`tools` に定義、呼び出しは `tool_calls`、結果は `tool` メッセージ。システムプロンプトから `# Tools` の説明を外す）／テキスト形式（Qwen 形式。`tools` は送らない）。どちらでも、ツールの説明は 1 回だけ。端末のモデルの会話は変わらない（変換は provider に渡す直前の `ChatMlBridge` だけ）。結果が返らなかった呼び出し（途中で止めた会話）は、テキストに戻して送る。
- **思考を返す**：各返信の思考を `AssistantTurn.reasoning` に残し（DB schema 3）、プロンプトの文字には入れず、`GenerateRequest.assistantReasoning` を通して provider の assistant メッセージの `reasoning_content` にする。モデルの設定「過去の思考を返す」：自動（DeepSeek・GLM で、ツールが function calling のとき）／常に返す／返さない。根拠は、DeepSeek の `encoding`（ツールを宣言すると過去の思考を全部残す）と、GLM の `clear_thinking: false`。

### 7.5 チャットからプロバイダーを追加する（0.8.5）

- 道具 `add_provider`（`name`・`base_url`・`models`・`tools`）。呼ぶと確認カードが出て、「追加する」を押したときだけ保存する。保存は必ず**新しい id の追加**で、既存のプロバイダーは変えない。使用中のプロバイダーも切り替えない。
- **既存のプロバイダーを変える道具は作っていない**（編集は設定画面だけ）。理由：チャットに紛れ込んだ指示で、API キーが保存済みのプロバイダーの URL を書き換えられると、キーが別のサーバーに送られるため。
- API キーの欄は無い（スキーマにも入れていない）。`base_url` に `user:pass@`・`?api_key=`・`#…` があれば拒否する。`/chat/completions` まで貼ってあれば落とす。ヘッダーと追加のリクエスト項目も、この道具では入れない。確認カードは URL をそのまま出す（キーを後で入れたときの送り先を、利用者が見て確かめられる）。

### 7.6 モデルの一覧・フォールバック・トークンの事前チェック・思考のメニュー（0.9.0）

- **SSE の UTF-8**：本文は `Utf8Decoder`（ストリーム版）で読む。以前は chunk ごとに復号していて、日本語（3 バイト）が chunk の境目で切れると `FormatException: Unfinished UTF-8 octet sequence` で返信が止まった（Gemini と、分担で多発）。境目を 1・2 バイトずらした 2 つのテストで再現する。
- **モデルの一覧（`catalog`）と、使うモデル（`models`）は別**。`catalog` は `/models` で取れた一覧（`ProviderConfig.catalog`、取得時刻 `catalogAt`）、`models` は上限・思考・プロンプトなどを設定した、使うモデル。一覧から選ぶと、`ProviderStore.selectModel` が `models` に写す。何百件もの一覧を、設定を持つ `models` に入れないため。
- **自動取得**：設定「モデル一覧を自動で読む」（`modelListAutoFetch`）と「再取得の間隔（時間）」（`modelListRefreshHours`）。起動時に、古くなった一覧を背景で読む。プロバイダを保存したとき（そのプロバイダの欄「一覧を自動で読む」が入っていれば）、すぐ読む。MCP サーバーを保存したときは、すぐ道具の一覧を読み（`probeMcp`）、その大きさ（トークン数の見積もり）を知らせる。
- **ツリー表示と検索**（`lib/ai/model_catalog.dart`、`model_tree.dart`、`lib/ui/model_tree_view.dart`）：モデル名の作者（`anthropic/`・`google/`・`deepseek-ai/` など、接頭辞）で分けて、Claude・Gemini・DeepSeek …の折りたたみにする。8 件以下の提供元は分けない。検索欄は大文字小文字を区別せず、空白で区切った語をすべて含むものが残る（`claude opus`）。提供元の名前にも当たる（`orca claude` は Orca の Claude 系）。検索中はすべての折りたたみを開く。コーディングモードの選択画面は、上に「最近使った」（`ProviderStore.recentRefs` 順。`markUsed` が返信を作るたびに記録。数は設定 `recentModelCount`、0 で出さない）と、提供元ごとのツリー。
- **フォールバック**（`lib/ai/fallback.dart`）：ルール `FallbackRule { from, targets, statuses }`。`from` と `targets` は `provider|model`、`provider|*`、`*` のどれか。具体的なルールが優先（モデル > 提供元 > `*`）。切り替える失敗の既定は 401・403・404・408・429、5xx すべて、接続の失敗。**返信の最初の 1 文字が来る前の失敗だけ**切り替え、書き始めたあとは切り替えない（途中まで書いたモデルのまま）。切り替えると、チャットに「A が 403 のため B に切り替えました」と出す。設定「フォールバックを使う」（`fallbackEnabled`）で一括して止められる。コーディングモードの設計・開発の役割にも効く。
  - **ルールの編集は設定画面（詳細）だけで、チャットからは変えられない**。会話の内容が別の提供元に送られるため、チャットの指示で送り先を足されると、プロンプトインジェクションで会話が外に出せてしまう（`add_provider` と同じ理由。7.5）。
- **トークンの事前チェック**（`lib/ai/token_budget.dart`）：送る前に、指示とツール定義の長さを見積もる（UTF-8 のバイト数 ÷ 3。目安）。モデルの文脈（`contextTokens`）がわかるモデルだけ。(1) 指示＋ツールが文脈の「割合」（設定 `tokenOverheadPercent`、既定 80%）を超える、または (2) 会話＋余白 256 が文脈を超える、のとき、**送らずに**エラーにする。エラーには、どの MCP サーバーのツール定義が大きいかを含める。設定 `tokenPrecheck` で止められる。見積もりは目安で、モデルのトークナイザとは違うので外れうる（割合を上げるか、チェックを止めて使う）。**実際のモデルとの照らし合わせは未**。
- **道具の呼び出しの繰り返し**：以前は「ラウンド数」（既定 4）で止めていて、検索を言い換えて 4 回するだけで「4 回を超えた」と止まった。いまは、**同じ道具・同じ引数の呼び出し**が繰り返されたときだけ止め、引数が違えば止めない。ラウンドの上限（`maxToolRounds`）は暴走の安全弁で、既定 30（保存済みの 4 は 30 に上げる）、最大 200。
- **思考の表示**：返信の上の「思考プロセス」を、既定で**開いたまま**にした（設定 `thinkingExpanded`。オフにすると、返信が始まったあとは折りたたむ。タップで開閉）。見出しに文字数を出す。`reasoning_content` または `reasoning` の欄を読む（7.1）。出さないモデルや、思考の送り方が未設定のモデルでは、出ないことがある。
- **入力欄の「思考」ボタン**（`lib/ui/thinking_sheet.dart`。RikkaHub の推論の選択に近づけた）：押すとシートが開く。オンラインのモデル：「考える量」（オフ／自動／その送り方が書いている強さ：DeepSeek・Z.ai は 低・高・最大、そのほかは 低・中・高）、「送り方」（`ThinkingFormat`）、送り方が未設定のときは提供元のアドレス・モデル名からの推測のボタン。選ぶと、そのモデルの `ThinkingConfig` に保存される（詳細の設定と同じ）。端末のモデル：思考のスイッチと、速度⇔精度のスライダー。送り方を変えると、新しい形が知らない強さ（DeepSeek の `medium` など）は外れる。
- **OpenRouter 形**（`ThinkingFormat.openRouter`）：`reasoning: {effort: low|medium|high}`、オフは `reasoning: {enabled: false}`。OpenRouter の公式 docs をこの環境から開けず、**リクエストの形は未確認**。実際のリクエストで確かめること（違えば「追加のリクエスト項目」で上書きできる）。
- **「詳細」画面**（`lib/ui/model_detail_page.dart`）：提供元ごとの一覧の取得、フォールバックのルール、トークンの事前チェック、MCP のコストの確認。入口は、モデルの一覧のシートと、思考のシートの「モデルの詳細設定」。
- 表示の言い換え：「モデル未導入」は「ローカルモデル未導入」（端末のモデルが無いとき。オンラインのモデルを使っているときは、そのモデルの名前を出す）。

- **Gemini の「not JSON: Unexpected character」（0.9.4）**：Gemini の OpenAI 互換エンドポイントは、1 つの返信で複数の道具を呼ぶとき、すべての呼び出しの `index` を 0 にして、`id` だけで区別する（実機のエラーから分かったこと。公式の仕様は確認できていない）。アプリは `index` ごとに引数をつないでいたので、2 つの呼び出しが `{...}{...}` になり、JSON として読めなかった。`openai_compatible.dart` は、同じ `index` に**別の `id`** が来たら別の呼び出しにする。`id` も無く、つながって届いたものは、同じ道具の引数として `{...}{...}` を分ける（`splitObjects`。文字列の中の括弧は数えない）。**1 回のラウンドで実行する道具は 1 つ**なので、1 つの返信に複数の呼び出しがあれば、最初の 1 つを実行する（以前は最後の 1 つだった）。読めなかったときのエラーには、本文の冒頭 120 文字も出す。
- **再起動でモデルの選択が戻る不具合（0.9.8）**：`ProviderStore.save` が、保存した提供元が**使っていないものでも**「選んだモデル」を、その提供元の最初のモデルに書き換えていた。起動のたびに、背景でほかの提供元のモデル一覧を保存する（自動取得）ので、選んだモデルが最初のモデルに戻り、その状態が次の保存で残ることがあった。いまは**提供元ごとに選んだモデルを覚え**（`providers.chosen`。古い保存の `providers.activeModel` も読む）、保存で動くのはその提供元の選択だけ（そのモデルが消えたときに限り、最初のモデルに戻る）。別の提供元へ行って戻っても、選んだモデルが残る。
- **Gemini の HTTP 400（0.9.5。原因は推定）**：検索のあとの 2 回目のリクエストが HTTP 400 になった（実機）。Gemini 3 系は、道具の呼び出しに暗号化された**思考署名**を付けて返し（`tool_calls[].extra_content.google.thought_signature`。出典：VS Code の issue https://github.com/microsoft/vscode/issues/296713 、Google の開発者フォーラムの報告。公式 docs はこの環境から開けず、**フィールドの形・ストリームでの位置は未確認**）、次のリクエストでそれを返さないと 400 になる、という報告が複数ある。標準の OpenAI クライアントはこの欄を落とすので、アプリも落としていた。対応：呼び出しに付いた `extra_content` を**そのまま**取っておき（`ToolCallDelta.extraContent`。呼び出しの JSON の `extra_content` として履歴に残す）、次の送信の `tool_calls` にそのまま入れる。署名の無い提供元には何も足さない。**これで直るかは未確認**。同時に、失敗のメッセージが出ない問題も直した：Gemini はエラーを `[{"error": {...}}]` とリストで包むことがあり、本文を読めずに「HTTP 400」だけ出ていた。リストの先頭を読み、形が分からなければ本文の頭 300 文字を出す。直らなくても、次は理由が画面に出る。

### 7.7 プロンプトのキャッシュと使用量（0.12.7）

- きっかけ：「キャッシュはそれに加え API 自体のキャッシュ対応がされているならそれを使うようにします」。
- **仕組み（提供元の側）**：OpenAI 形式の提供元の多くは、**同じ先頭（system → 道具 → 会話）**を続けて送ると、その分を自動でキャッシュから読み、安くて速くなる（OpenAI は 1,024 トークン以上、DeepSeek も自動）。**アプリが送る側でできるのは、先頭を変えないこと**。確認したところ、プロンプトに時刻などの毎回変わる文字は入っておらず、会話は後ろに足すだけなので、**同じ会話の中では先頭が安定している**（`ChatMlPromptBuilder`・`ChatMlBridge`）。先頭が変わるのは、(1) **エージェントが変わったとき**（メッセージごとに選び直すので、役割の指示が変わる。キャッシュは最初から作り直し）、(2) 設定（口調・追加の指示・最大文字数）やモデルを変えたとき、(3) 会話を**要約したとき**（4 章）。
- **読むもの**：提供元の応答の使用量（`usage`）から、キャッシュで読まれたトークン数を**書いてあれば**読む：`prompt_tokens_details.cached_tokens`（OpenAI 形式）、`prompt_cache_hit_tokens`（DeepSeek 形式）。無ければ「分からない」（0 とは別に扱う）。`UsageDelta.cachedTokens` → `Usage`（`GenerationEvent`）→ `RunMeter.usage` → 返信の進み具合の行に **「入力 12,340 トークン（キャッシュ 9,800）」**（返信が続いている間と、終わったあとの 1 行）。以前は、使用量の値は捨てていた（どこにも出ていなかった）。**端末のモデルと、使用量を返さない提供元は、この表示が出ない**。分担の開発モデルの分は数えていない。
- **送るもの（`prompt_cache_key` など）**：キャッシュの当たりを良くするために提供元が受け取る送信側の項目（OpenAI の `prompt_cache_key`・`prompt_cache_retention` など）は、**アプリは勝手に付けない**（知らない項目を 400 で断る互換サーバーがあるため）。使いたいときは、提供元の編集画面の「追加の本体（body）」に自分で書く（既存の仕組み。固定の値になる）。Anthropic の `cache_control`（ブレークポイントを自分で指定する方式）は、OpenAI 形式の窓口では使えないので**未対応**（Anthropic 用のアダプタが無い）。
- **未確認（この環境からは、公式の資料に届かなかった）**：OpenAI（`platform.openai.com`）と DeepSeek（`api-docs.deepseek.com`）の公式ドキュメントは、このセッションのネットワークでは名前を解決できず、読めなかった。上の項目名は、公式の説明を覚えている範囲のもので、**実機で実際の応答を見て確かめる必要がある**。Gemini の OpenAI 互換の窓口が、キャッシュの数を `usage` のどこに出すかは、Google の資料でも確認できなかった（Google の標準の応答では `cached_content_token_count`。`https://ai.google.dev/gemini-api/docs/caching`）。読めない形なら、表示が出ないだけで、動作には影響しない。

## 8. 設定の方針：機密情報以外は全て設定できる

- **設定できないのは機密情報だけ**：API キー、GitHub トークン、MCP トークン、検索 API のキー。これらは安全な領域（`flutter_secure_storage`）に置き、設定の JSON・バックアップ・チャットのどこにも出さない。プロバイダの追加ヘッダーに `Authorization` や `x-api-key` のような（機密になりうる）名前は書けない。
- **それ以外は全て、設定画面から変えられる**。上限・タイムアウト・件数・サンプリング・プロンプト・モデルの選択・プロバイダのヘッダーとボディ。**コードに固定の数字を足すときは、設定も足す**。これまで固定だった値の例：添付（ファイル数・文字数・画像の MB）、検索結果の件数、通信・MCP・オンラインモデルのタイムアウト、ツールの繰り返し検出、更新ダウンロードの試行回数と無通信の判定、DRY、**Linux 環境（0.12.1 で設定にした。15 章）**。
- **チャットからも変えられる**（`update_settings`。変更はカードで見せ、承認してから反映）。対象は `AgentSettings.specs`（`lib/core/settings_spec.dart`）。チャットから変えさせないものは `blocked`（`lastModelPath`・`updateRepo`・`kvCache`・`errorReportEnabled`・`errorReportRepo`・**`shellConfirm`・`linuxRootfsUrl`・`linuxRootfsSha256`**）に理由つきで置く。プロバイダーは、**チャットからは追加だけ**できる（7.5）。
- **設定の読み書きの道具**（0.5.x）：
  - `get_settings`：変更できる設定を、現在値・ラベル・選択肢（日本語ラベル付き）・範囲つきで返す。プロバイダ構成・モデル一覧・MCP サーバー（URL・有効/無効・ツール名）・検索 API（名前・URL の `?` より前・有効か・キーの有無）も読める。**キーとトークンは伏せる**。承認は不要。
  - `update_settings`：1〜6 件の変更を提案し、**承認するまで何も書かない**（毎回）。承認待ちは `UiMessage.settings` として会話に保存され、再起動しても残る。適用は `withSettings(current, changes)` が JSON に書いて `AppSettings.fromJson` に型を決めさせるだけ（キーごとのコードは無い）。モデルに返す文には、いま何になったか（`theme=ダーク` など）と、「次にモデルを読み込んだときから有効」な項目（`contextLength` など）を入れる。
  - API キーを変える口は作らない（読み書きとも不可）。
- **ローカルとオンラインは別々**：端末のモデルは `local*`（temperature・top_p・top_k・min_p・DRY・最大トークン・追加プロンプト）、オンラインは `online*`（temperature・top_p・最大トークン・追加プロンプト）。優先順位は、オンライン＝モデルごとの設定 ＞ `online*` ＞ 既定、ローカル＝`local*` ＞ 既定。端末専用：コンテキスト長・スレッド・HyperLoad・GPU・KV キャッシュ・Force Execution。`AppSettings.toGeneration(modelParamsB, cloud: engine.isCloud)` が、答えるモデルの側を選ぶ。
- モデルごとに **画像を送る** スイッチ（6.3）。プロバイダには、ツール呼び出しの対応・追加ヘッダー・追加のリクエスト項目（JSON）の編集画面。
- 主な設定の例：`downloadConnections`（ダウンロードの同時接続数、既定 4）、`updateUseDelta`、`resumeDownloadsOnStart`、`fontScale`、`autoInstallUpdate`、`maxToolRounds`。

## 9. コーディングモード（プランナーモデル＋開発モデル）

**プランナーモデルが細かく分けて、複数の開発モデルに並列に渡す。アプリは呼び出しの手伝いだけをする**（0.10.0 で、アプリが固定の手順で進める方式から作り直した。0.12.4 で、細かい分割・依存・複数の開発モデル・並列・「聞かずに自分で決める」・Mermaid の図に作り直した。利用者の指示は 19.6）。

```
依頼（Coding エージェント）
  └ プランナー（入力欄で選んだモデル。固定もできる）が答える（道具・思考・停止・ストリーミングはふつうのチャットと同じ）
       ├ 小さな依頼・質問 → 自分で答える
       └ 大きな依頼 → 道具 delegate を 1 回呼ぶ
            plan（Mermaid の図）＋ summary（共通の決めごと）＋ tasks（id・題・指示・待つ相手）
                a["モデル"] ──┐
                b["API"]  ────┼──▶ d["画面"] ──▶ e["テスト"]      （矢印 a --> d ＝ d は a の結果を待つ）
                c["設定"]（待たない：すぐ始まる）
            待たない仕事は、空いている開発モデルへ**すぐ**渡る（モデル A・B・C … に分け合って同時に）
            待つ仕事は、前の仕事の**結果を渡されて**から始まる
         開発モデルは、聞かずに自分で決めて実装し、結果だけを返す
         結果は、番号（d1, d2 …）つきでプランナーに返り、図とファイルはユーザーに見える
       └ プランナーが読んで、本当に間違っていれば delegate を revise つきで呼ぶ／よければ短くまとめて終わる
```

- **アプリがすること**（`lib/ai/delegation.dart` の `DelegateRunner`）：(1) 開発モデル（複数）とその上限を持つ。(2) 仕事を**空いたモデルへ順に**渡す（`_Pool`。1 つのモデルが同時に受ける数は、設定「1 つの開発モデルが同時に走らせる数」とモデルの上限の小さいほう。端末のモデルは 1）。いちばん空いているモデルを選び、全部埋まっていれば空くのを待つ。(3) **依存**を守る：矢印の先の仕事は、前の仕事が終わってから始まり、その結果（題と答え。長さは「プランナーが読む結果の長さ」まで）を、自分の依頼の前に付けて渡される。前の仕事が失敗したら、その先は**実行せず**「前の仕事 dN が失敗したため」と返す。(4) 結果に番号を付けて覚える（200 件まで）。`revise` は、元のタスク・前の答え・直す内容を渡し直す。(5) 図（プランナーが書いたもの。無ければ依存から描いたもの）とファイルを、プランナーの答えの途中に**そのままユーザーに見せる**（`ToolOutcome.shown`。Mermaid のコードブロック）。(6) **質問は返さない**：開発モデルが `QUESTION:` で答えたら、プランナーには聞かずに「誰も答えられない。いちばん妥当な選択で、完全なファイルを今出して」と **1 回だけ**伝える。それでも質問なら、その仕事を失敗として返す。(7) **失敗は別のモデルへ**：モデルが失敗（接続・空の答え）したら、その仕事を、まだ試していない別のモデルに渡す（1 回）。(8) 1 件が失敗しても、ほかの結果は返す。(9) 停止で全部の開発モデルを止める。
- **分割の図**（`lib/core/plan_graph.dart`）：Mermaid の `flowchart` のうち「これが先、次にあれ」を言う部分だけを読む（節点 `a["題"]`・`a[題]`・`a(題)`・`a{題}`・`a`、矢印 `-->`・`---`・`==>`・`-.->`（ラベル付きも）、`a --> b & c`、`a --> b --> c`）。スタイル・subgraph などは読み飛ばす。**矢印 `a --> b` は「b は a の後」**。図とタスクの `depends_on` は合わせて使う。図が読めない（節点が無い）・図に載った id がタスクに無い・待つ相手がタスクに無い・**輪（循環）になっている**ときは、理由を付けて断り、プランナーに書き直させる（下の「失敗でエラーにしない」）。図は、ほかの道具（ローカルの opencode など）に**同じ文章のまま**渡せる形にしてある（0.12.9 で、それを使う）。
- **失敗でエラーにしない**（0.12.4）：プランナーが書いた道具の呼び出しが使えない（図が読めない・タスクに指示が無い・輪になっている・許可されていない道具など）とき、返信を**エラーで終わらせず**、「使えなかった理由」をアプリの注として伝えて書き直させる（`retryLimit` 回まで。画面には「道具の呼び出しが読めませんでした（理由）。書き直します」が出る）。回数を超えたら、いままでどおり理由を出して止める。ふつうの道具にも効く。開発モデルの失敗は、結果として返り、全部失敗したときは「自分でやるか、もっと単純な仕事に分けて」とプランナーに伝える。
- **アプリがしないこと**：分け方を決める、結果の良し悪しを判断する、直させるかを決める。これらはプランナーの判断。アプリがプランナーに伝えるのは、道具の使い方と上限だけ（`CodingPrompts.plannerInstructions`：小さな依頼は自分で答える／大きいときは delegate を 1 回／**細かい目標に分ける**（1 ファイルか関数のまとまり）／Mermaid の図で分ける・待たない仕事を増やす／同時に走る仕事は互いを見られないので名前・シグネチャ・データ形式は要約と各タスクに書く／開発モデルは聞かずに決める／ファイルはユーザーに見えるので答えに写さない／直す回数は N 回まで）。
- **どのモデルが答えるか（プランナー）**：**既定は、入力欄で選んだモデル**（設定「プランナーは、使用中のモデルに合わせる」＝オン）。オフにすると、設定の**プランナーモデル**に固定され、そのときだけ Coding エージェントの依頼は固定のモデルが答える（`RoutingEngine.planner`）。**0.12.4 で、オンを既定にした**：利用者の報告「分担を使った後は、モデルを切り替えても前のモデルを使い続ける」の原因が、プランナーが設定で固定されていて、入力欄の切り替えが Coding の依頼に届かないことだったため。以前に固定していた人も、設定の保存値に項目が無いので、オン（追従）になる。`delegate` の道具とプランナーへの指示は、Coding エージェントで、コーディングモードが使えるとき（オン・開発モデルが 1 つ以上使える・プランナーが決まっている）だけ出る。
- **安くなる理由・速くなる理由**：長いコードを書くのは開発モデル（安い・端末のモデルなら無料）。プランナーの出力は短い指示と確認だけ。開発モデルには、会話の全体ではなく**要約とそのタスク（と、待った相手の結果）**だけを送る。細かく分けて、複数のモデルで同時に書くので、速い。
- **端末のモデルの扱い**：端末のモデルは同時に 1 つのチャットしか使えない（`ExclusiveLease`）。開発モデルの中に端末のモデルがあれば、`delegate` の実行の間だけ借りる。**ほかのチャットが使っていれば、その模型は使わず、ほかの開発モデルが仕事を受ける**（全部が端末のモデルなら、プランナーに「使用中」と返す）。
- 役には、オンラインの各モデルも端末のモデルも選べる（`provider|model`、端末は `local|`）。
- **設定**：オン/オフ、プランナーは使用中のモデルに合わせる（既定オン）、プランナーモデル（オフのとき）、開発モデルと**追加の開発モデル**（`developerModelsMore`。1 行に 1 つ。設定画面では「開発モデルを追加」）、タスクの最大数（既定 **8**、最大 16。超えた分は断り、プランナーに伝える）、1 つの開発モデルが同時に走らせる数（既定 **4**）、書き直しの回数（既定 1。0 で「直させない」と伝える。伝えるだけで、数えて止めはしない）、開発モデルの最大トークン（**0 ＝ 自動**）、プランナーが読む結果の長さ（既定 12000 文字/件）。チャットの入力欄に「分担」ボタン。変えてよい項目は、チャットからも変えられる（`AgentSettings`）。
- 実装：`lib/core/coding_plan.dart`（設定・プロンプト・`questionIn`・`filesIn`）、`lib/core/plan_graph.dart`（図）、`lib/core/protocol.dart`（`delegate` の道具と読み取り・検査。`Protocol.schemaVersion` は 6）、`lib/ai/roles.dart`（`RoleModel`）、`lib/ai/delegation.dart`（`DelegateRunner`・`_Pool`）、`lib/core/chat_controller.dart`（使えない呼び出しの書き直し）、`AppController`（`_plannerEngine`・`_developerRoles`・`_SessionToolRuntime`）。
- **同じ計画を、コマンドラインのエージェント（opencode など）に渡す**（0.12.9。きっかけ：「それらの分割指示は、ローカルで opencode などを呼び出す時にも同様に使えるようにしたい」）：プランナーの指示に、「利用者が頼んだときは、同じ計画（図、そのあとに各タスクの指示とファイル）を `/workspace/PLAN.md` に書き、`shell_session`（一発で終わる使い方があれば `run_command`）でそのエージェントに渡し、終わるまで画面を読む。図が依存を表すので、その順に進めさせる」と書いた（`CodingPrompts.plannerInstructions`）。Mermaid は多くの CLI エージェントがそのまま読める形なので、図を作り直す必要はない。**アプリが PLAN.md を自動で作る機能は作っていない**（書くのはプランナー）。**未確認**：opencode・agy が、この rootfs（Ubuntu 24.04 arm64、proot）に入って動くか、どう呼ぶのが正しいか（このセッションでは、それらの公式の資料に届かず、確かめていない）。
- **未確認**：実際のモデルで、プランナーが図とタスクの id を正しく合わせて書くか（小さいモデルは崩しやすい。崩したときは上の書き直しで直す）、複数の開発モデルでの実際の速さ、`QUESTION:` を返すモデルが、「決めて」と言われたあとに作れるか、開発モデルの出力が長いときのユーザーへの見え方。Mermaid の図は、いまは**コードブロック**で見せる（図としての描画はまだ。コピーして mermaid の表示器に貼れる）。
- 既知の制限：トークンの使用量・費用の表示はまだない。Coding エージェントには、ファイルを読み書きする道具が無い（**0.12.0 で `run_command` が入ったので、Linux 環境の中なら書ける**）。開発モデルの温度は 0.2 に固定（モデルの設定・メーカーの推奨があればそちらが優先。設定にするのは今後）。

## 10. 外部との連携：MCP・Kaggle・検索・エラーの報告・GitHub Actions

### 10.1 MCP（外部ツール。0.6.0 → 複数サーバー 0.8.0）

- `lib/mcp/mcp_client.dart`：JSON-RPC 2.0 over HTTP（Streamable HTTP）。`initialize` → `notifications/initialized` → `tools/list` / `tools/call`。応答は JSON でも SSE（`data:` 行）でも読む。認証は `Authorization: Bearer <token>`。
- `lib/mcp/mcp_tools.dart`：サーバーのツールをアプリの `ToolDefinition` に変換する。名前は `mcp_<サーバー id>__<ツール名>`（id に `__` は使わせない。衝突を避ける）。`tools/list` はサーバーごとにキャッシュ。失敗したサーバーは、そのターンだけ外す（チャットは止めない）。呼び出しの失敗は `tool_response` としてモデルに返す。
- 設定：`mcpServers: [{id, name, url, enabled, approveWrites}]`。トークンは `mcp_token_<id>` で secure storage。旧 `mcpUrl` は `id=default` の 1 台に移行する。MCP サーバーの追加画面に「Kaggle を入れる」「GitHub を入れる」のひな形、「確認」ボタン（つながるか・道具の一覧が取れるか）。
- **書き込みの道具は、実行の前に確認カード**（`ToolApproval.needsApproval`）。道具の名前を**単語ごと**に分け（`create_or_update_file` も `CreateBenchmarkTaskFromPrompt` も）、書き込みを表す単語（create・update・delete・submit・start・cancel・stop・run・upload・publish・save・post・send ほか。`ToolApproval.writeVerbs`）に当たるかで判定する。以前の部分文字列の判定は、`ListDatasets` が「set」で確認になり、Kaggle の `Submit` / `Start` / `Cancel` が確認にならなかった。サーバー自体の id は読まない。サーバーごとの「書き込みの前に確認する」スイッチは既定オン。
- 端末のモデル（llama.cpp）では、MCP の複雑な JSON Schema が GBNF に重いので、**クラウドのモデル推奨**。stdio トランスポートは Android では難しい。
- 未対応：OAuth（GitHub のホスト型サーバーは OAuth 前提のことが多い。いまは PAT をベアラーで送るだけ）。

- **道具が多いときは、探して呼ぶ**（0.12.8。きっかけ：「mcp サーバーの内容を見て呼び出せるようにして、事前プロンプトを削減しましょう」）：MCP の道具の定義は、毎回の送信に全部載る（GitHub の公式サーバーだけで数十個、数千トークン）。**定義の合計が `mcpOnDemandTokens`（既定 2000 トークン。0 で常に）を超えるとき**（設定 `mcpOnDemand`、既定オン）は、定義を送らず、**3 つの道具**だけを渡す：`mcp_find`（`query`・`server` で探す。名前と 1 行の説明）、`mcp_describe`（1 つの道具の説明と引数の JSON Schema）、`mcp_call`（`tool` と `arguments`。呼ぶ）。`mcp_find` の説明に、サーバーの id・名前・道具の数が書いてある（何かあることを、モデルが知るため）。**`mcp_call` は、チャットが受け取った時点で、サーバーの道具そのものの呼び出し（`McpCall.unwrapped`）に直す**ので、**確認カード・「次から確認しない」・実行は、本当の道具に対して働く**（書き込みの道具は、これまでどおり承認を待つ）。**`mcp_call` で届くのは `mcp_<サーバー>__<道具>` だけ**で、`run_command`・`update_settings` などアプリの道具には届かない。結果の長さは、既存の設定「MCP の結果の上限」で切る。**やらなかったこと**：proot の中に `mcp` コマンドを置いて、コマンドから MCP を呼ぶ形。proot の中のコマンドは承認カードを通らずに MCP の道具（push など）を呼べてしまい（proot は境界ではない。15.4）、トークンを rootfs に置くか、橋渡しの口を開けることになるため。事前プロンプトの削減は、上の 3 つの道具で、承認を保ったまま実現できる。必要なら、利用者の指示で足す（19.5）。**未確認**：実機の、小さなモデル（端末）が「探す → 読む → 呼ぶ」の順を守れること（守れないときは、設定でオフにする）。
- **道具の結果がファイルのとき**（0.9.8）：以前は結果の `text` だけを読み、画像などだけの結果は、結果の JSON 全体（base64 を含む）をそのままモデルに渡していた。いまは `McpClient.describeResult` が読む：`text` はそのまま。`resource`（結果の中のファイル）は、テキストなら中身（`[file: アドレス (種類)]` の下に）、バイナリなら説明だけ。`resource_link` は名前とアドレス。`image` / `audio` は種類と大きさだけ（**バイト列は渡さない**。モデルは読めず、何十万文字ものトークンになる）。`content` が無ければ `structuredContent`。全体は設定「MCP の結果の上限」（`mcpResultMaxChars`、既定 30000 文字）で切り、何文字省いたかを書く。**画面には出さない**：ファイルそのものを表示・保存する機能は無い（画像の表示は未対応）。

- **文字化けの修正（0.12.1）**：MCP の応答を `response.body` で読んでいた。`package:http` は応答の `Content-Type` に charset が無いと **Latin-1 で復号する**ので、GitHub の MCP サーバー（`application/json` を charset 無しで返す）の、ファイルの中の日本語が全部化けた（AI が読むと `ã‚µãƒ¼ãƒãƒ¼` のようになる）。`_request` は `utf8.decode(response.bodyBytes, allowMalformed: true)` で読む。同じ理由で、`lib/core/http_get.dart` の GET も UTF-8 固定にした（POST は先に直っていた）。**未確認**：直ったことを確かめたのは、0.12.0 を入れた端末のアプリから（`settings_spec.dart` の日本語が正しく読めた）。GitHub 以外のサーバーでも同じ。

### 10.3 オンライン検索（0.8.6〜0.8.12）

- きっかけ：「検索に失敗（ローカル AI のみで回答）: DuckDuckGo Instant Answer: no results」。検索の順が SearXNG（アドレスを入れたときだけ）→ DuckDuckGo Instant Answer で、Instant Answer は百科事典のような要約と関連項目だけを返す API（普通のキーワード検索の結果一覧は返らない）。アドレスが空だと、ほぼ空の答えだけが残っていた。
- **検索 API を自由に登録できる**（設定 → 検索設定）：1 件の項目＝名前、URL、メソッド（GET / POST）、ヘッダー（JSON）、本文のひな形（POST）、API キー、「結果の場所」、題名・URL・概要の項目名、1 回の件数の上限（`maxCount`）、使う／使わない。URL・ヘッダー・本文の `{query}` が検索語、`{count}` が件数、`{key}` が API キーに入れ替わる（本文の中は JSON の文字列／数字として安全に入る）。結果の場所と項目名はドット区切り（`web.results` など。答えそのものが一覧なら空）。本文が JSON にならないときは保存の前に分かる。「試す」で、保存の前に 1 回検索して読み取れた件数を表示する。

### 10.4 エラーの自動報告（0.11.0。GitHub Issue）

- きっかけ：「エラーログの内容は GitHub の issue に自動送信するように」。アプリが落ちたとき・返信に失敗したときに、**1 件の Issue**（既定は `keusidan/arce.ai`）を作る。実装は `lib/core/error_report.dart`（報告の形・隠す処理・送るかの方針）と `lib/services/error_reporter.dart`（送信・上限・待ち行列）、`lib/services/error_hooks.dart`（Flutter / Dart の捕まえ損ねたエラーの受け口）。
- **送るもの**：エラーの種類（`crash` 捕まえ損ねた／`chat` 返信の失敗／`test` 設定画面の確認）、エラーのクラス名、短いメッセージ（400 字まで）、スタックのうちアプリ内の行（10 行まで）、状況（アプリの版・OS・端末か online か・プロバイダのホスト・モデル名）。**会話（質問・答え・ファイル）は送らない**。全ての文字列は `ErrorRedactor` を通す：キー・トークン・`Authorization`・既知のキーの形（`sk-`、`ghp_`、`github_pat_`、`AIza…`、`xox…`）・32 字以上の連続した英数字を `[removed]` / `[key]` / `[long-token]` に、URL はホストだけ残してログイン・パス・クエリを落とす。隠し過ぎる側に倒してある。
- **送るかの方針**（`ErrorPolicy`）：捕まえ損ねたエラーは、ネットワークの失敗（接続切れ・名前解決・タイムアウト）以外は送る。返信の失敗は、**アプリ側の不具合らしいものだけ**（HTTP 400 / 422、`not JSON`、プログラムの例外など）。API キーの誤り・401・403・404・429・5xx・タイムアウト・トークン超過のような、利用者の設定や相手側の事情のものは送らない。
- **同じ問題は 1 つの Issue**：署名（種類・クラス・数字や ID を除いたメッセージ・先頭のフレームの FNV-1a。HTTP の番号は残す＝400 と 422 は別の問題）が同じなら、新しい Issue を作らず**コメント**で件数を足す。同じ署名の報告は `errorReportMinHours`（既定 6 時間）に 1 回まで、全体で 1 時間に `errorReportMaxPerHour`（既定 5 件）まで。上限は設定画面（「エラーの報告」）とチャットの `AgentSettings` から変えられる。
- **送れなかったとき**：401・403・404 は、トークンかリポジトリが変わるまで止める（毎回失敗しない）。429・5xx・ネットワークは**待ち行列**（最大 20 件、端末に保存）に入れ、次の機会に送る。それ以外の失敗は捨てる。設定画面に直近の結果の一覧と「テスト送信」がある。
- **トークンは更新用と別**：Issue の作成には、**この 1 つのリポジトリだけ**に Issues: Read and write を付けた fine-grained のトークンを使う。リリースの更新用のトークンとは共有しない。secure storage（`github_issue_token`）に入り、設定の JSON・バックアップ・チャットには出ない。トークンが空なら送らない（設定画面に理由を表示）。
- **チャットからは変えられない**：`errorReportEnabled` と `errorReportRepo`（送り先）は `blocked`。書き換えられると、エラーの内容が別のリポジトリに送られるため。分や件数の上限だけがチャットから変えられる。
- **注意**：公開リポジトリの Issue は誰でも読める。メッセージにプロバイダのホストとモデル名が入る。非公開にしたいときは、送り先を非公開のリポジトリにする。
- 出典：Issues の作成 https://docs.github.com/en/rest/issues/issues#create-an-issue ／ コメントの作成 https://docs.github.com/en/rest/issues/comments#create-an-issue-comment ／ fine-grained のトークンの権限 https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens ／ レート制限 https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api ／ Flutter のエラー処理 https://docs.flutter.dev/testing/errors
- **未確認**：実際の GitHub への送信（テストは HTTP の応答を差し替えたもの）。トークンの権限が足りないときの応答、実機で捕まえ損ねたエラーが受け口に届くこと。

### 10.5 GitHub Actions の読み取り（`ci_status`、0.12.0・0.12.1）

- きっかけ：CI の赤を直すたびに、利用者が失敗したステップを写して渡していた。アプリに登録している GitHub の MCP サーバー（`api.githubcopilot.com/mcp/`）には **Actions の道具が無い**（トークンに全権限を渡していても、サーバーが公開していないため出てこない）。そこで、アプリ自身の道具として足した。
- `lib/services/ci_client.dart`：GitHub REST の `/repos/{owner}/{repo}/actions/runs`（`per_page`、`branch`）と `/actions/runs/{id}/jobs` を読むだけ（**書き込みはしない**）。`CiRun`（名前・イベント・ブランチ・短い SHA・状態・結論・URL）と、`CiJob`（状態・結論・**失敗したステップの名前**）。
- 道具 `ci_status`：引数 `repository`（既定は `keusidan/arce.ai`）・`branch`・`limit`（既定 10）・`run_id`。`run_id` を渡すとその実行のジョブと失敗したステップを返す。**読み取りだけなので、確認カードは出さない**。道具名は `mcp_` で始まらないので、MCP の道具と衝突しない。`ToolCallParser` は `run_command` と同じく、`McpCall` として扱って `McpTools` に渡す。
- トークン：`AppController._ciToken` が、**GitHub の MCP サーバーに入れてあるトークンをそのまま使う**（`id`/`name` が github、または URL が `githubcopilot.com` / `api.github.com`）。見つからなければ空で、**公開 API**（未認証）で読む（公開リポジトリなら足りる）。
- 応答は **UTF-8 で復号する**（10.1 と同じ理由。GitHub は charset を付けない）。
- **未確認**：`Actions: Read` が無いトークンで 403 になるときの文言（`HTTP 403（トークンの権限に Actions: Read があるか確かめてください）` を出す）、非公開リポジトリでの動作（未認証では読めない）、実機での表示。
- なぜ MCP のサーバーを替えないか：Copilot 版の MCP には Actions が無く、セルフホストの `ghcr.io/github/github-mcp-server` にはあるが、この環境からは確かめられていない。アプリ側に 1 つの道具を足すほうが小さく済む。

## 11. 更新とダウンロード

### 11.1 アプリ内更新

- `UpdateService`：リリースの一覧（`/releases?per_page=50`）を読み、**自分の OS のタグ**の中で最も新しい版を選ぶ。起動時と、起動中は設定の間隔（既定 12 時間）で確認する。ダウンロードは、手動の確認では利用者が承認してから。`<ファイル>.sha256` で検証してから、インストール。
- **自動で更新する**（`autoInstallUpdate`、既定オン、0.5.2）：自動のチェックで新しい版を見つけたら、そのまま download → 検証 → install まで進む。手動の「確認する」は従来どおり（カードの「ダウンロード」を押してから）。iOS は自動では動かさない。Android は初回だけ、システムの画面で「この提供元を許可」が必要（許可前は `UpdateReady` のまま残り、許可後に「インストール」で入る）。失敗は `UpdateFailed` に理由が残り、画面に出る。
- Android は PackageInstaller（同じ署名鍵の APK だけ受け付けられる）。Windows・macOS・Linux は、展開して、アプリの終了を待ち、ファイルを入れ替えて、再起動するスクリプトを走らせる（`desktop_installer.dart`。アプリを置いたフォルダに書き込めることが条件。`C:\Program Files` のような場所では入れ替えに失敗して元の版のまま再起動する）。iOS はリリースページを開くだけ。macOS は、自己更新のために App Sandbox を切っている（`macos/Runner/*.entitlements`）。
- 非公開リポジトリのときは、設定の「GitHub トークン」（`Contents: read`）が要る。アセットのダウンロードは、リダイレクト先にトークンを送らないよう、手でリダイレクトを追う。トークンは端末の安全な領域に保存される。
- 起動時に、いま動いている版のダウンロードと古い版のファイルを削除する。再開に使える新しい版の `.part` は残す。デスクトップは展開完了後にアーカイブを削除する。
- 同じ署名鍵で更新すれば、モデル・DB・設定はそのまま引き継がれる。

### 11.2 ダウンロードの部品（0.8.8〜0.8.16）

**起きたこと**：Android で、ブラウザなら 100 Mbps 出る回線で、アプリのダウンロードが 1 Mbps ほどしか出なかった（更新もモデルも）。両方が遅いので、1 本の接続そのものが遅いと考えた（1 本の TCP は、パケットが落ちる回線や往復が長い回線で大きく遅くなる）。**本当の原因は端末で測れていない**。以下は、この仮説への対策。

- `FileDownloader`（`lib/services/file_downloader.dart`）：**モデルのダウンロードと更新が共有する**部品（0.8.15。以前は別々に同じ処理を持ち、0.8.13 のモデル側の直しが更新に入っていなかった）。1 つのファイルを、範囲要求（`Range`）に答える取得元から、大きければ**複数接続**で、途中のファイルから続きを、失敗したら**自動で取り直して**埋める。完成済み・長すぎる部分ファイル・サーバーが範囲を無視（200）・416 の扱い、無通信の判定、最後まで届かなかったことの検出、別 isolate での SHA-256 もここ。
- `SegmentedDownload`：同じ大きさの部分に分け、部分ごとに別の接続で取り、各部分を `<名前>.part.seg<番号>of<個数>` に書き、最後に連結する。1 部分は 4 MB 以上（小さいファイルは分けない）。中断しても部分ごとに取れた分が残る。接続数を変えたら前の部分ファイルは捨てる。サーバーが `Range` を無視したら 1 本に戻る。**部分ファイルは、パスの文字列ではなく、ファイルの名前で見分ける**（Windows では同じフォルダが `/` でも `\` でも書ける）。
- `DownloadErrors`（`CancelToken`、取り直す失敗の判定 `isTransient`、画面に出す文 `explain`）：取り直すのは、通信の失敗とサーバーが忙しいとき（HTTP 5xx・429）だけ。404 や 403、一時停止は取り直さない。エラーの文からは、CDN の署名付き URL（数百文字）を消す。
- 設定：「ダウンロードの同時接続数」（既定 4、1〜16。1 で従来どおり）、「ダウンロードの試行回数」（既定 3）、「ダウンロードの無通信の判定」。
- モデル側（`ModelDownloader`）に残るのは、Hugging Face のどこにあるか・大きさと SHA-256 を聞くこと・チェックして置くこと。更新側に残るのは、GitHub の API からの転送先の辿り方・`.sha256` の確認・差分更新・インストール。別のまま：HTTP クライアント（`http.Client`）は、モデルの取得・更新・検索・天気がそれぞれ持つ。
- **モデルのダウンロードが止まる問題**（0.8.13）：完成済みの `.part` に「続きから」の範囲要求を出して HTTP 416 で断られていた → 同じ大きさなら再取得せずチェックへ、長ければ捨てて最初から。接続を閉じられると手で「再開」が要った → 自動で取り直す。SHA-256（数 GB）を画面と同じスレッドから別 isolate に移した。
- **アプリを閉じているあいだも続ける**（0.8.14）：以前は、返信の生成と更新のダウンロードだけが前面サービスに載っていて、モデルのダウンロードは載っておらず、他のアプリを開くとプロセスが止められていた → モデルのダウンロードも前面サービスに載せた（通知「モデルをダウンロード中」）。**アプリを閉じて（最近使ったアプリから消して）止まったダウンロード**は、次の起動で取れた分から自動で続ける（設定「止まったダウンロードを次の起動で続ける」、既定オン）。ダウンロード中は、モデルの隣に目印のファイル（`<モデル名>.running`）を置き、終わる・一時停止すると消す。残っていれば、閉じて止まったもの。起動時、途中までのファイルがある未完成のモデルは「再開」の状態で出す。
  - **まだできないこと**：最近使ったアプリから**消した瞬間**、Android は画面と Flutter のエンジン（Dart のコード）を壊す。前面サービスはプロセスを残すが、ダウンロードをしている Dart のコードは止まる。消している間も進めるには、ダウンロードを Kotlin のサービスの中で行う（または Flutter のエンジンをサービスが持ち続ける）必要がある。実機で試せない環境では、起動できなくなる危険があるので入れていない。

### 11.3 差分更新（0.8.9・Android）

- **リリース側**：新しい APK を作ったあと、直近 3 つの前のリリースの APK から新しい APK への **bsdiff** のパッチを作り、同じリリースに載せる。名前は `ARCE.AI-v<新>-android.apk.from-<旧>.patch`。パッチが APK の半分より大きければ載せない。作るのに失敗しても、リリースは止めない（`continue-on-error`）。0.8.19 から、これは別ジョブ `patches`（12 章）。例：v0.8.19 のリリースには 0.8.16 / 0.8.17 / 0.8.18 からのパッチが付き、0.8.18 → 0.8.19 のパッチは 10 KB、0.8.17 → 0.8.18 は約 1.1 MB（APK は約 138 MB）。
- **アプリ側**（`UpdateService._tryDelta`）：①このリリースに、今の版向けのパッチがあるか調べる（なければ全体）。②インストール済みの APK の場所を聞く（`SystemBridge.kt` の `baseApk`。分割 APK でインストールされていれば無し）。③パッチをダウンロード（複数接続・再開は同じ経路）。④今の APK にパッチを当てて、新しい APK を作る（`lib/services/bspatch.dart`、別 isolate）。⑤新しい APK の SHA-256 を、リリースの `.sha256` と比べる。**一致したときだけ**使う。一致しない・途中で失敗した・土台が違う、のどれでも、作りかけは消して、**これまでどおり全体をダウンロード**する。
- パッチの形式は BSDIFF40（`bsdiff` や Python の `bsdiff4` が作る標準の形式。bzip2 の読み取りに `archive` パッケージ）。設定：「差分だけダウンロードする」（`updateUseDelta`、既定オン）。
- 確認済み：実際の `bsdiff4` が作ったパッチを、Dart が 1 バイトも違わずに適用できる。土台が違うとき・壊れたパッチを拒否する。
- **未確認**：インストール済みの `base.apk` が、リリースの APK とバイト単位で同じか（同じでなければ SHA-256 が合わず全体を取る）。実機で `baseApk` が読めるか。大きな APK にパッチを当てるときの時間とメモリ（古い APK・新しい APK・パッチを全部メモリに載せる）。ネイティブのライブラリ（`.so`）が毎回違うバイト列になると、パッチは小さくならない（実際には上のとおり小さくなっている）。
- 「キャッシング（差分更新）」は、この差分更新のこと。ビルドのキャッシュは別（12 章）。

## 12. リリースと CI

### 12.1 タグと Release（プラットフォームごとに別）

| OS | タグ | ファイル |
|---|---|---|
| Android | `vX.Y.Z` | `ARCE.AI-vX.Y.Z-android.apk`（arm64 と x86_64 を 1 つにした署名付き）＋ `.sha256` ＋ 差分パッチ |
| iOS | `ios-vX.Y.Z` | `ARCE.AI-vX.Y.Z-ios-unsigned.ipa`（未署名） |
| Windows | `windows-vX.Y.Z` | `ARCE.AI-vX.Y.Z-windows-x64.zip`（`Release` フォルダの中身＋ VC++ ランタイム DLL） |
| macOS | `macos-vX.Y.Z` | `ARCE.AI-vX.Y.Z-macos.zip`（`ARCE.AI.app`。ad-hoc 署名・公証なし） |
| Linux | `linux-vX.Y.Z` | `ARCE.AI-vX.Y.Z-linux-x64.tar.gz` |

- **Android のタグだけ接頭辞なしで、「Latest」にする**：前の Kotlin 版のアプリ（v0.3.x が端末に入っている）が `releases/latest` の `vX.Y.Z` と `.apk` を読むため。他の OS は `--latest=false`。Flutter 版のアプリは、`releases` の一覧から自分の OS の接頭辞のタグの中で最も新しい版を選ぶ。
- どのファイルにも `sha256sum` 形式の `.sha256`。
- 版は `X.Y.Z` のみ（Windows が版を数字として埋め込むため `-beta` は使えない）。
- **Android の `versionCode` ＝ 主版 × 1,000,000 ＋ 副版 × 1,000 ＋ 修正版**（0.4.0 は 4000）。ワークフローの実行番号を使うと、分けたときに 1 から始まり、以前の APK（14 以下）より小さくなって、Android が更新を拒否する。

### 12.2 ワークフロー

- `ci.yml`：push と PR で `flutter analyze` と `flutter test`。
- `release-android.yml` / `-ios.yml` / `-windows.yml` / `-macos.yml` / `-linux.yml`：それぞれ、判定（`.github/actions/prepare`）→ 解析とテスト → ビルド → 公開（`.github/actions/publish`：その OS の Release にアップロード。Release が無ければ作る）。5 つは**同時並行**で別々に動く（2 章）。同じ OS の実行どうしだけ `release-<os>-publish` で順番になり、待ちは最新の 1 つだけ残る（**push の間隔が詰まると、古い待ちの実行が取り消される**。0.8.7 と 0.8.8 の 1 回目が Android に出なかったのはこのため。次の版は、前の Android の実行が動き始めてから push する）。
- **同じ OS の run は順番に動き、待てるのは 1 つだけ**（`concurrency` で `cancel-in-progress: false` にしているため）：ビルドが動いている間に、同じ OS の run が 2 つ以上来ると、**真ん中の run は `cancelled`** になる（失敗ではなく、より新しい run に席を譲ったという扱い）。2026-10-27 に、Linux のビルド（0.9.8。約 25 分かかった。Android などは約 7 分）の最中に 0.10.0 → 0.10.1 → 0.10.2 を続けて push し、**0.10.0 と 0.10.2 の Linux が `cancelled`**（その版の Linux のリリースが無い）になった。さらに、**`main` への fast-forward も、同じ版の release の run を作る**（作った版が既にリリース済みなら、準備の段階で何もせず終わるが、待ち行列の席は取る）ので、待っていた新しい版の run を押しのけた。**だから**：(1) 版を続けて push するときは、Linux のビルドが終わってから。(2) `main` に送るのは、ブランチの release がすべて終わってから（AGENTS.md の「リリースが終わったあと」の理由の 1 つ）。(3) 席を失った版の Linux は、Actions の「Release Linux」を手動で起動（`workflow_dispatch`、版を入力）して作れる。
- **Android は 5 つのジョブ**（0.8.19 から）：`prepare`（4 秒）→ **`test`（解析とテスト、約 73 秒）と `android`（ビルド、約 5 分）が並行** → `publish`（15 秒。`test` が成功、または `reuse_run` で省略したときだけ）→ `patches`（別ジョブ。差分パッチを、前の 3 つの版ごとに並行して作り、リリースに足す。約 68 秒。失敗しても全体は赤にならない。`continue-on-error`）。以前は test → build → patches を直列で行い、約 9 分かかっていた。他の 4 つは、ビルドのジョブの最後のステップで公開する。
  - 公開だけが失敗したら「Re-run failed jobs」で公開だけをやり直せる（25 分のビルドとそのキャッシュは無駄にならない）。`reuse_run` に実行番号を入れた手動実行は、ビルドを省いて、その実行の APK（Artifact `android`、7 日間）を公開する（版が違う APK は拒否する）。
  - Android のジョブは、最初に使わないソフト（.NET、Haskell など）を消して、ディスクを空ける（llama.cpp のコンパイルで容量が足りなくなったため）。ccache は `cache/restore` と `cache/save`（`if: !cancelled()`）に分けて、ビルドが失敗しても保存する（`save-always` は非推奨で動かなかった）。NDK のキャッシュ、Gradle のキャッシュ、Flutter / pub のキャッシュも使う。他の OS は Flutter SDK と pub のキャッシュだけ。
  - 一度、「Set up ccache」の apt で 26 分以上止まったことがあり、取り消して再実行した（以降は正常）。
- きっかけ：`pubspec.yaml` の変更を push（どのブランチでも）、OS ごとのタグ、手動実行（dry run あり）。Android は `release-android.yml` と `prepare` / `publish` の変更でも動く（失敗後の再試行。workflow を直して push すると、その版の Android が動き直す）。判定：その OS の Release に、その OS のファイルが既にあれば、push では何もしない（`main` への fast-forward で起動した実行が数秒で終わるのはこのため）。
- 各ワークフローは、自分のビルドの前に解析とテストを行い、通らなければ公開しない。

| 方法 | 動作 |
|---|---|
| `pubspec.yaml` の `version:` を上げて push | 5 つが動き、自分の Release にまだ無いファイルだけをビルドする。失敗した分は、修正を push すれば足りない分だけ作り直される |
| `git tag v0.5.0 && git push origin v0.5.0` | Android だけが動く（iOS は `ios-v0.5.0` など、OS ごとのタグ） |
| Actions タブ →「Release Android」などで「Run workflow」 | 選んだワークフローだけ、入力した版（空なら `pubspec.yaml` の版）で動く |
| Android の「Run workflow」で `reuse_run` を入力 | ビルドせず、その実行の APK を公開 |
| 「dry run」にチェック | Release は作らず、ビルド結果を Artifact（7 日間）に残すだけ |

### 12.3 最初に 1 回だけ行うこと

- **Android の署名鍵**：Secrets `ARCE_KEYSTORE_BASE64`・`ARCE_KEYSTORE_PASSWORD`・`ARCE_KEY_ALIAS`（登録済み。Kotlin 版と同じ鍵）。Flutter 版も同じ `applicationId` と鍵で署名するので、端末の Android 版（v0.3.x）に上書きインストールできる。Secrets が無いと、署名なしの APK では更新できないので、workflow はエラーで止まる（dry run を除く）。
  - 鍵の作り方：`keytool -genkeypair -v -keystore arce-release.jks -keyalg RSA -keysize 4096 -validity 36500 -alias arce`。**`arce-release.jks` と鍵のパスワードは、なくすと二度と更新を配れなくなる**。PC とは別の場所にもバックアップを取る。リポジトリには置かない。
  - Secrets への登録：`base64 -w0 ~/arce-release.jks | gh secret set ARCE_KEYSTORE_BASE64`、`gh secret set ARCE_KEYSTORE_PASSWORD`（入力を求められる）、`gh secret set ARCE_KEY_ALIAS --body arce`。ブラウザなら Settings → Secrets and variables → Actions → New repository secret。
  - debug 版からの切り替え：debug 鍵で署名された版は、release の APK で上書きできない。一度アンインストールする（アプリ内のモデルも消える）。
- **Actions の権限**：Release の作成には `contents: write` が要る（workflow に書いてある。組織の設定で読み取り専用に固定されていたら Settings → Actions → General → Workflow permissions を確認）。ビルドのジョブは読み取りだけで、書き込みは公開のジョブだけ。
- 無料枠：非公開リポジトリの Actions は、無料プランで月 2,000 分。macOS のランナーは実行時間が 10 倍で数えられる。

### 12.4 `.github/workflows/` を変えたコミットにはタグを付けられない

`GITHUB_TOKEN` は `workflows` 権限を持てないので、`.github/workflows/` のファイルを追加・変更したコミットには、タグ（＝Release）を付けられない（API は `403 Resource not accessible by integration`、`git push` は `refusing to allow a GitHub App to create or update workflow ... without workflows permission`）。ただし**ブランチの先頭のコミットは対象外**（2026-10-04 に、使い捨ての検証用ワークフロー（実行 37194771866 / 37194843041 / 37195030866）で切り分けて確認した）：

| 条件 | 結果 |
|---|---|
| 先頭のコミットを指定（push 起動でも手動起動でも） | 成功 |
| ワークフローを変えた古いコミットを指定（`gh release create`、API、`git/refs`、`git push`） | すべて失敗 |
| ワークフローを変えていない古いコミットを指定 | 成功 |
| `--target` にブランチ名（＝先頭）を指定 | 成功 |

- 25 分のビルドの途中で同じブランチに push すると、ビルド中のコミットは先頭でなくなる。そのコミットが workflow を変えていると、公開が断られる（v0.1.0 と v0.4.0 の最初の試行がこれで失敗した）。
- 直し方（`.github/actions/publish`）：まずビルドしたコミットにタグを付け、断られたらその時点のブランチの先頭に付け直す（Release の本文に「ビルドしたコミット」を書く）。
- 自分でタグを押すときは、workflow を変えていないコミット（例：版を上げただけのコミット）に付ける。workflow を直して push したあとは、ビルド中にさらに push しないほうが確実。
- 未確認：人が先に押したタグ（`git push origin vX.Y.Z`）に対する公開。

### 12.7 リポジトリの bot（0.12.10。`bot.yml`）

- きっかけ：「github apps の bot で Claude みたいなことをしたい」「返信に加えて、修正の Pull Request を作る」（2026-10-29 JST。メモの「bot 連携」）。
- **使い方**：issue か Pull Request のコメントに `@arce-bot やってほしいこと` と書く。bot は、スレッド（題・本文・直近 20 件のコメント）とファイルの一覧を読み、モデルに聞き、**コメントで返信する**。変更を頼まれたときは、**`bot/issue-<番号>-<題>` という自分のブランチ**にコミットして、**下書き（draft）の Pull Request** を開く。自分が作った Pull Request（`bot/…`、同じリポジトリ内）には、続けて直しを足せる。**マージも、`main` への書き込みも、しない**。手動：Actions → Bot → Run workflow（issue の番号・指示・**dry run**。既定は dry run：何も書かず、ログに「こうする」を出す）。
- **構成**：`.github/workflows/bot.yml`（起動と鍵の受け渡しだけ）、`tool/bot/bot_core.dart`（**何をしてよいかの判断**：呼べる人・書けるファイル・上限・モデルの答えの読み取り・プロンプト。ネットワークに触れない純粋な部分）、`bot_runner.dart`（一連の流れ。GitHub とモデルは窓口 `BotGitHub`・`BotModel` の向こう）、`bot_github.dart`（REST API）、`bot_model.dart`（OpenAI 互換のチャット）、`bot.dart`（入口）。テスト：`test/tool/`（47 件。偽の GitHub・偽のモデル・`MockClient`）。
- **安全の設計**（`AGENTS.md` の「workflow はコミットを push しない」規則の**唯一の例外**。限度が規則）：
  1. **呼べる人**：`OWNER`・`MEMBER`・`COLLABORATOR` のコメントだけ。見知らぬ人が issue を書くことはできても、bot を動かせない（モデルが、リポジトリの秘密を使える場で、その人の文章を読むため）。bot 自身・他の bot のコメントでは動かない（ループの元）。引用行（`> …`）の中の `@arce-bot` は呼び出しにならない。判断は workflow の `if:` と、スクリプトの `BotPolicy` の**二重**。
  2. **モデルの出力は、データ**：書けるのは、**`lib/`・`test/`・`docs/`・`README.md` だけ**（変数 `BOT_ALLOWED_PATHS` で変えられるが、下の禁止は消せない）。**どんな設定でも書かない**：`.github/`（workflow を書けると、bot が自分に何でも許せる）、`AGENTS.md`・`CLAUDE.md`（規則）、`pubspec.yaml`・`pubspec.lock`（**`pubspec.yaml` を書くと、5 つの OS のリリースが始まる**）、`.git/`、鍵の入るファイル（`.env*`・`*.jks`・`*.pem`・`key.properties` …）。パスは、相対・`..` や空の部分なし・200 文字まで。1 ファイル 100 KB、合計 400 KB、12 ファイルまで。全体のファイルで、1 つの悪いファイルが他を巻き込まない（悪いものだけ「書かなかった」とコメントに出る）。**issue の文章に「.github を書き換えてよい」と書かれても、限度は変わらない**（テストあり）。
  3. **書き込み先**：`RestGitHub.commit` は、`bot/…` という名前のブランチにしか書かない（呼び出し側が何を渡しても。`main` などは、App のトークンが書ける権限を持っていても届かない）。**強制 push はしない**（動いた枝は、上書きせずエラー）。作る Pull Request は**下書きだけ**。
  4. **鍵**：GitHub への書き込みは、**GitHub App のトークン**（短命。このリポジトリだけ）で行う。workflow の `GITHUB_TOKEN` は**読み取り専用**。モデルの API キーは Actions の secret。コメントの文章は、**シェルのコマンド行に入れない**（bot は、GitHub が渡す event のファイルを読む）。
  5. 変更には「モデルが書いた。実行していない。読んでからマージして」と、コミットメッセージと PR の本文に必ず書く。
- **一度だけ必要な設定（利用者の作業。私にはできない）**：
  1. GitHub App を作る（Settings → Developer settings → GitHub Apps → New GitHub App）。名前は任意（呼び出しの `@arce-bot` は文字列で、App の名前と一致していなくてよい）。Webhook は「Active」を**外す**。権限（Repository permissions）：**Contents: Read and write**、**Pull requests: Read and write**、**Issues: Read and write**、Metadata: Read-only。作ったら、**秘密鍵（.pem）を生成**し、**このリポジトリだけにインストール**する。
  2. このリポジトリの Settings → Secrets and variables → Actions に、**Secrets**：`BOT_APP_PRIVATE_KEY`（.pem の中身）、`BOT_API_KEY`（モデルの API キー）。**Variables**：`BOT_APP_ID`（App の ID）、`BOT_API_URL`（OpenAI 互換のチャット補完のアドレス。例：`https://api.openai.com/v1/chat/completions`）、`BOT_MODEL`（モデル名）。任意：`BOT_EXTRA_BODY`（提供元の追加の項目を JSON で。例：`{"reasoning_effort":"low"}`）、`BOT_ALLOWED_PATHS`（空白区切り）。

- **やらなかったこと**：(1) 他人のフォークの Pull Request への書き込み（フォークの枝には書けない。書かない）。(2) 自動マージ。(3) ファイルの削除・リネーム（全ファイルの書き込みだけ。影響を小さくする）。(4) 画像や大きなファイルの読み書き。(5) モデルに道具を渡して試行錯誤させる形（テストを実行させるなど。安全の面が広がる。いまは「読む → 答える」を最大 3 回まで）。
- **未確認（この環境からは試せない）**：GitHub App の作成・権限・`actions/create-github-app-token@v2` の動き、実際のモデルが JSON の形で答えるか（答えなければ「使える答えを作れなかった」と返す）、Git Data API の呼び出しの順（偽の通信でしか試していない）、CI が bot の枝で走ること（App のトークンの push は、`GITHUB_TOKEN` の push と違って、他の workflow を起こす）。**最初の 1 回は、dry run で確かめてから使うこと**。

### 14.1 点検（2026-10-29。0.12.5）

利用者の指示（19.6 の 08:18「バグや実装漏れ、脆弱性をしっかり治しておいてください」）で、**次の範囲**を読んで点検した。全体の監査ではない。

**直したこと（0.12.5）**
1. **リンクを開く先が何でもよかった**：返信や検索結果のリンクを、`launchUrl` でそのまま開いていた。モデルや検索結果は他人の文章なので、`intent:`（他のアプリの起動）・`tel:`・`sms:`・`file:`・`content:`・`javascript:` も開けた。→ `safeWebUri`（`lib/core/safe_url.dart`）で **http(s) だけ**にした。ユーザー名つきの address（`https://good.example@evil.example/`）も断る。アップデートの Release ページも同じ。
2. **試作ページの入口が推測できた**：生成した HTML を `127.0.0.1` で配る `PreviewServer` のページ番号が `0, 1, 2 …` の連番だった。同じ端末の**ほかのアプリ**は、ポートさえ分かれば番号を順に引いて、ほかの人のコードや文章を読めた。→ アドレスを **128 ビットの乱数**にし、`Host` が `127.0.0.1` でない要求（DNS リバインディング）を断り、`Cache-Control: no-store`・`Referrer-Policy: no-referrer` を付け、残すページ数に上限（設定 `previewMaxPages`、既定 50）を付けた（以前は無制限に溜まった）。
3. **`run_command` の「サンドボックス内」の判定が抜け道だらけだった**：`/proc/self/root/data/data/ai.arce.app/…` のように書けば、確認なしで端末側のファイルを読めた（15.4）。→ `/proc` の入口（`root`・`cwd`・`exe`・`mem`・`environ`・`fd` …）を名指ししたら確認にした。さらに、**外部の文章を読んだあとは確認**にした（設定、既定オン）。proot が境界ではないことを 15.4 に書いた。
4. **DNS の設定がチャットから変えられた**（`linuxDns`）：変えられると、Linux 環境の名前解決を好きな先に向けられる。→ チャットからは変えられない（`blocked`）。
5. **承認カードまわり**：①「実行する」が、押してもしばらく何も変わらずフリーズに見えた（カードが残る）→ 押した瞬間にカードを消して「ツールを実行しています」を出す。②道具が例外で終わると、返信全体が落ちた→ 失敗として、モデルに伝える。③実行中に押した「停止」が、次の依頼の前に忘れられた→ 次の依頼を送らずに止まる。④ボタンを 2 回押すと、道具が 2 回走りえた→ 1 回だけ答える。⑤引数が Map の `toString` のまま出て、長いファイルの中身が画面を占領した→ 引数を 1 行ずつ、長いものは折りたたんで「全文を見る」。（①の強制終了は 0.11.2。）
6. **http のままキーやトークンを送る設定に、警告が無かった**：MCP サーバーとプロバイダの編集画面に、「このアドレスは暗号化されません」を出す（家の中・localhost は出さない）。
7. 設定ファイルに `approvedTools` として `run_command` などを書いても、**読み込むときに外す**（確認を飛ばせるのは MCP の道具だけ）。

**点検したが、問題が見つからなかったもの**：`allowBackup=false`・サービスは `exported=false`・公開しているのは MainActivity だけ・PendingIntent は immutable・SQLite の全文検索は引数を束縛して検索語を組み立てている・デスクトップの更新の展開は SHA-256 を確かめたアーカイブだけを `tar`/`ditto` に渡す・設定の JSON にキーやトークンは入らない・エラー報告は送る前に隠す（10.4）。

**直していない・残っていること**
- **proot が境界でない**ことは、直せない（Android のアプリは、namespace や chroot を使えない）。確認とカードで守る。上の 15.4。
- コマンドの**通信を止められない**（proot にその機能が無い）。外部の文章に誘導されたコマンドが、ワークスペースの中身を外へ送れる。確認（外部を読んだあと）が、いまの唯一の備え。
- 会話履歴の DB は暗号化していない（アプリの専用領域に置く、ふつうの扱い）。端末が root 化されていれば読める。
- **点検していない範囲**：`bspatch`（壊れた差分への耐性）、`ApkInstaller`、MCP クライアントのリダイレクトの扱い、`desktop_installer` のスクリプト、Hugging Face のダウンロード、**依存パッケージの既知の脆弱性**（`pub` の一覧を調べていない）、iOS/macOS の権限設定。

### 15.3 設計

```
モデル --(tool: run_command)--> McpTools._runShell --> LinuxEnvironment --(MethodChannel)--> Kotlin: SystemBridge
                                                                                          └ LinuxEnv.run
                                  nativeLibraryDir/libproot.so  <--   (APK に同梱した実行ファイル)
                                  filesDir/linux/rootfs/            (ダウンロードして展開)
                                  filesDir/workspace/               (/workspace として見せる。全チャット共通)
```

- **実行ファイル**：proot 本体と loader を `libproot.so`、`libproot_loader.so` の名前で `jniLibs/arm64-v8a/` に置き、起動時は `nativeLibraryDir` から `ProcessBuilder` で実行する。
- **rootfs**：初回に利用者が「Linux 環境を入れる」を押したとき（または最初の `run_command` のとき）、既存の `FileDownloader`（再開・複数接続・SHA-256 検証）でダウンロードし、Kotlin 側で展開する。APK には入れない。**Ubuntu**（`pip` や `apt` が使いやすい。容量は Alpine より大きい）。
- **展開**：`..` や絶対パスを含む名前は拒否する。シンボリックリンクが展開先の外を指さないか確かめる。
- **仕上げ**：`/etc/resolv.conf`（設定の DNS）、`/etc/hosts`、`/etc/hostname`、`/etc/apt/apt.conf.d/99arce`（`APT::Sandbox::User "root";`）、`/workspace`、`/tmp`。
- **実行**：`proot --kill-on-exit --link2symlink -0 -r <rootfs> -b /dev -b /proc -b <workspace>:/workspace -w <cwd> /usr/bin/env -i HOME=/workspace/home PATH=… LANG=C.UTF-8 TERM=dumb TMPDIR=/tmp SHELL=/bin/bash /bin/bash -c <command>`。標準出力・標準エラー・終了コードを別々に返す。127 は「proot または rootfs が使えない」。
- **互換モード**：端末の seccomp で起動に失敗したとき `PROOT_NO_SECCOMP=1` で再試行する（設定 `shellCompatMode`）。
- **proot の入手**：`termux/proot` の特定の版（タグ）を**サブモジュール `third_party/proot` に固定**し、CI で**ソースからビルド**して `.so` として APK に入れる（libtalloc は、apt が署名を確認する Ubuntu のソースパッケージからビルドする）。出所がソースまで辿れ、GPL のソース提供がリポジトリで済む。Termux の配布 `.deb` から取り出す案は、バイナリの出所が第三者になり、方針（公式の一次情報だけを土台にする）に合わないので採らない。
- **パッケージングへの影響（測定済み。15.8）**：`android/app/build.gradle.kts` は `useLegacyPackaging = true`（`.so` をインストール時に端末へ展開する。`execve()` には実ファイルが要るため。15.8 のとおり、端末内の合計は今より小さくなる）。

### 15.4 安全面

モデルが shell を実行できるようになるため、次を設定にし、既定は厳しくする（8 章の方針）。

- 確認カード：既定は毎回確認する（`shellConfirm`。チャットからは変えられない）。確認カードには、モデルの説明ではなく、**実際のコマンド**を表示する（`ToolApproval.tile` が `$ command`・場所・上限の秒数を出す）。
- 作業フォルダ：`/workspace` だけが端末のファイルに繋がる。アプリの他のデータ（設定、API キー、DB）は見せない。
- 時間の上限と出力の上限（設定項目：`shellTimeoutSeconds`・`shellMaxTimeoutSeconds`・`shellMaxOutputChars`）。
- ネットワーク：rootfs の中は端末の回線で外に出られる。**止める設定は作っていない**（proot にその機能が無く、作れない）。既定は許可。
- **API キー・MCP の token は、既定では rootfs に渡さない**（ファイルにも環境変数にも入れない）。**例外：利用者が設定した「秘密」だけを、そのコマンドを承認したときに、そのコマンドの環境変数として渡す**（0.12.8。下の 15.11）。API キー（プロバイダ）は、秘密にできない（選べるのは、MCP サーバーのトークンと、自分で入れた値だけ）。
- **proot は境界ではない**（0.12.5 の点検で、はっきり書く）：コマンドはアプリと同じ利用者（uid）で走り、proot が変えるのは**パスの読み替えだけ**。`/proc` を bind しているので、コマンドは `/proc/self/root` や `/proc/<pid>/cwd` を通って**端末の本当のファイル（アプリのデータ・履歴 DB・ダウンロードしたモデル）に届く**。`SandboxPolicy` は、コマンドの**文字**にそれらが書かれていれば「サンドボックスの外」として確認を求める（`/proc/self|thread-self|<pid>|$$|${VAR}|$(…)` の `root`・`cwd`・`exe`・`mem`・`environ`・`fd` など）が、**変数で名前を組み立てられると防げない**。API キーと MCP のトークンは、端末の安全な領域（Keystore で暗号化）にあり、環境変数でもファイルでも rootfs には渡していないので、コマンドからは読めない。読めるのは、履歴・設定（キーを含まない）・モデルなど。
- **外部の文章に書かれた命令**（検索結果・MCP の返答。誰かが「このコマンドを実行して」と書けてしまう）への備え（0.12.5）：**検索や外部ツールの結果を一度でも読んだ会話では、サンドボックス内のコマンドも確認する**（設定「検索や外部ツールの結果を読んだあとは、コマンドを確認する」。既定オン。`shellConfirmAfterExternal`。チャットからは変えられない）。保存した会話を開き直したときも、履歴に外部の結果があれば同じ。確認カードに理由が出る。止めるのは確認までで、確認したあとの実行は制限しない。

### 15.11 コマンドに秘密を渡す（0.12.8）

- きっかけ：「mcp サーバーのトークンは proot 環境でも使用できるようにして欲しい」「mcp 以外に使用できると良いな」（2026-10-29 08:2x JST）。
- **設計**：設定（Linux 環境 →「コマンドで使う秘密」）に、**環境変数の名前**と**値のもと**を並べる。値のもとは、(a) ここで入力した値（端末の安全な領域 `shell_secret.<名前>`）、(b) いま登録してある **MCP サーバーのトークン**（同じトークンをサーバーとコマンドで使う。サーバーを消すと、その秘密も消える）。設定の JSON には**名前と、もとの MCP サーバーの id だけ**が入り、値は入らない（バックアップにも入らない）。
- **モデルが使う手順**：`run_command` の引数 `secrets: ["GITHUB_TOKEN"]` に**名前**を書く。モデルは名前（`run_command` の説明に並ぶ）だけを知り、**値は見えない**。使える名前は、値があるものだけ（`McpTools.secrets`）。使えない名前を書くと、**実行せずに**「使える名前はこれ」と返す。
- **承認は毎回**：`secrets` が空でないコマンドは、**サンドボックスの中で済むものでも、必ず承認カードを出す**（`approvalRequired`。`shellConfirm` がオフでも。`secrets` の形が崩れていても確認する）。カードに「**秘密を渡します: 名前…（このコマンドは、これらの値を読めます。送り先は制限できません）**」と出る。「次から確認しない」は、コマンドには出ない（従来どおり）。**チャットからは、秘密の一覧を変えられない**（`blocked` の `shellSecrets`）。
- **渡し方**：承認したコマンドの 1 回だけ。Android 側（`LinuxEnv.prootCommand`）が、`env -i` の引数に `名前=値` を足す（ファイルにも、ログにも書かない）。名前は Dart と Kotlin の両方で検査する（英数字と `_`、先頭は数字以外、64 文字まで。`HOME`・`PATH`・`LD_PRELOAD`・`BASH_ENV` など、アプリが決める／読み込みを変える名前は不可）。
- **出力の伏せ字**：コマンドの出力に、渡した値がそのまま出ていたら `[名前]` に置き換えてからモデルに渡す（4 文字以上の値だけ。`ShellSecrets.redact`）。**防げるのは、うっかり環境変数を表示したときだけ**。値を変換（base64 など）して出す、ネットワークで送る、といった意図的な持ち出しは防げない。**proot は境界ではない**（15.4）ので、渡したコマンドは、その値をどこへでも送れる。だから**承認の前にコマンドを読むこと**が唯一の歯止めで、画面にもそう書いてある。
- **0.12.9 で直した、0.12.8 の不具合**：`run_command` の引数を読む `_parseRunCommand` が、`secrets` を**捨てていた**（既知の引数だけで `McpCall` を作り直していたため）。0.12.8 のままでは、モデルが `secrets` を書いても、承認カードに名前が出ず、コマンドにも渡らなかった。単体テストが `McpCall` を直接作っていて、モデルが書いた JSON を読む経路を通していなかったので、気づけなかった。直して、**モデルの JSON から承認カードまで**を通すテストを足した（`test/core/protocol_test.dart`、`test/core/chat_controller_test.dart`）。同じ種類の見落としを防ぐため、新しい引数を足すときは、パーサを通すテストを必ず書く。
- 検討して**やらなかったこと**：(1) 秘密を、承認なしでコマンドに自動で入れる（外部の文章に書かれた命令で持ち出せてしまう）。(2) API キー（プロバイダ）を秘密にする（用途が無く、危険だけ増える）。(3) 通信先の制限（proot の外の仕組みが要る。15.4）。
- テスト：`test/core/shell_secrets_test.dart`、`test/mcp/mcp_tools_test.dart`（名前だけを教える・毎回承認・値は頼んだコマンドだけ・出力の伏せ字・使えない名前は実行しない）、`test/services/settings_test.dart`。**未確認**：実機で、`git push` などが渡した環境変数で認証できること、Kotlin 側（`LinuxEnv.kt`・`SystemBridge.kt`）の動き（CI のビルドは通るが、端末で動かしていない）。

### 15.12 対話セッション（0.12.9）

- きっかけ：「AI が opencode や agy などを使えるように、インタラクティブな実行にも対応させたい」（2026-10-29 08:2x JST）。
- **何ができるか**：`run_command` は 1 つのコマンドを実行して終わる（入力はできない）。新しい道具 `shell_session` は、**動き続けて入力を待つプログラム**（`python3` などの REPL、質問してくるインストーラ、opencode のような CLI エージェント）を動かし、モデルが**画面を見ながら入力**できる。`action`：`start`（`command`・`cwd`・`secrets`）→ セッション id、`send`（`session`・`input`・`keys`）、`read`（画面を見直す。動いている最中に使う）、`stop`、`list`。`input` は打ったとおりに入り（改行は Enter キー）、`keys` は名前（Enter・Tab・Esc・矢印・Home・End・PageUp/Down・Backspace・Delete・Space・Ctrl-C・Ctrl-D・Ctrl-<英字>）。`wait_ms` は出力を待つ時間（設定の上限まで）。
- **仕組み**：Android 側（`ShellSessions.kt`・`LinuxEnv.startSession`）が、proot の中で **`script -qefc "…" /dev/null`**（util-linux。基本システムに入っている）を動かして**疑似端末**を与える（`TERM=xterm-256color`、`stty` で桁・行を設定）。出力は**リングバッファ**に溜め、Dart 側が**バイト位置から**読む（二重に読まず、読み落とさない。バッファより多く出たときは「失われた」と伝える）。読むときは、出力が来るまで待ち、**来たあと 0.3 秒静かになるまで**待つ（出力は何回かに分かれて届くため）。モデルが読むのは**端末の画面を文字にしたもの**（`TerminalScreen`、`lib/core/terminal_screen.dart`）：色・カーソル移動・消去・行の挿入と削除・スクロール領域・保存と復元に対応し、色や題名などは捨てる。画面から流れた行は、次の読み取りで 1 度だけ渡す（`scrollback`）。全画面のプログラムは、その絵がそのまま画面になる。
- **安全**：**開始するコマンド**と、**入力する文**は、`run_command` と同じ規則で判断する（サンドボックスの外に触れる／`/proc` の抜け道がある／`secrets` を渡す／「検索や外部ツールの結果を読んだあと」の規則／すべて確認する設定、のどれかなら**承認カード**）。カードには、開始なら `$ コマンド`・場所・渡す秘密、入力なら `> 入力`・キー。**キーだけ**の入力（Ctrl-C・矢印）は、文が無いので聞かない。`read`・`stop`・`list` は聞かない。シェルを起動して、そこに文を打てば何でも実行できるので、**入力にも同じ判断をかけている**（文字の判定は、変数で組み立てた名前を防げない。15.4）。渡した**秘密の値は、画面にも流れた行にも出さない**（開始のときだけでなく、あとの読み取りでも伏せる）。開始時に環境が無ければ入れる（利用者が承認した呼び出しの中で）。
- **限度（すべて設定。「Linux 環境」のカード →「対話セッション」）**：同時に動かす数（既定 3）、使われないセッションを止めるまで（15 分。0 で止めない）、出力を待つ時間（1500 ミリ秒）と、モデルが指定できる上限（30 秒）、端末の幅・高さ（120×40）、流れた行を残す数（500）、読まれるまで残す出力（256 KB）。**ワークスペースが上限を超えたら、すべてのセッションを止める**（5 秒ごとに見る）。Linux 環境を削除する・ワークスペースを空にするときも、先にセッションを止める。
- 検討して**やらなかったこと**：(1) tmux を使う形（セッションの外のコマンドが、`--kill-on-exit` の proot ごと消えるため、サーバーを動かし続ける別の仕組みが要り、さらに tmux を apt で入れる必要がある）。(2) 全画面のプログラムの色や太字をモデルに伝える（読む役には要らない）。(3) アプリを閉じても続くセッション（プロセスは、アプリの終了とともに終わる）。
- **未確認（実機で確かめる）**：(1) proot の中で `script` が疑似端末を作れるか（`/dev/ptmx` と `/dev/pts` は `-b /dev` の経路で見えるはずだが、端末の SELinux の設定によっては断られるかもしれない）。(2) opencode・agy を、この rootfs に入れて動かせるか、どの呼び方が正しいか（公式の資料に届かず、未確認）。(3) 小さなモデルが「始める → 読む → 打つ」の手順を守れるか。(4) Kotlin（`ShellSessions.kt` など）の動き（CI のビルドは通るが、端末で動かしていない）。
- テスト：`test/core/terminal_screen_test.dart`（画面の読み取り 16 件）、`test/services/shell_sessions_test.dart`（読み取りの位置・キー・待ち時間・伏せ字・日本語の途切れ）、`test/mcp/mcp_tools_test.dart`（承認の規則・実行・失敗の返し方）、`test/core/protocol_test.dart`（モデルが書いた JSON の読み取り）、`test/core/chat_controller_test.dart`（外部の文章を読んだあとの確認）。

### 15.7 段階 1a の結果：proot のビルド（`proot-build.yml`、2026-10-26）

- 手順：NDK 29.0.13113456（sdkmanager）の clang（`aarch64-linux-android31`）で、①Ubuntu 24.04 のソースパッケージ `talloc`（2.4.2）を waf でクロスコンパイルして静的ライブラリにし、②サブモジュールの proot を、ソースフォルダのコピーの中でビルドする（`make proot loader/loader`）。結果は workflow の artifact `proot-arm64-v8a`（14 日）と、実行のアノテーションに出る。
- 結果：`libproot.so`（proot 本体）280,368 バイト、`libproot_loader.so`（loader）17,632 バイト（どちらも strip 後）。proot の動的な依存は `libdl.so` と `libc.so` だけ。PIE、`BIND_NOW`、LOAD の整列は 0x4000（16KB ページ対応）。loader は proot の中に埋め込まず別ファイル（`PROOT_UNBUNDLE_LOADER`）。実行時は環境変数 `PROOT_LOADER` でその場所を教える（fork のソース `src/execve/enter.c` で確認。未設定なら、ビルド時に決めた固定のパスを見に行く）。
- ビルドで必要だった回避（ソースは変えていない）：
  1. libtalloc の configure は、クロスコンパイルでは実行できない検査の答えを `cross-answers.txt` で求める。答えを入れた検査：uname、rpath、`--version-script`（FAIL）、getconf の大きなファイル、`HAVE_SECURE_MKSTEMP`、`C99 vsnprintf`、`strptime`、`HAVE_IFACE_*`、mmap 系（`HAVE_SHARED_MMAP`・`HAVE_MMAP`・`HAVE_MREMAP`・`HAVE_INCOHERENT_MMAP`）、`HAVE_FCNTL_LOCK`、`HAVE_FTRUNCATE_EXTEND`、`HAVE_BROKEN_READDIR`、`HAVE_WORKING_GETCWD`、`strtoll`。bionic（Android の libc）に当てはまる答えを、私の理解で入れた（実機で talloc を動かしての確認はまだ）。
  2. proot の makefile は、ソースフォルダの外でビルドすると VPATH のせいでパスが二重になる。→ ソースフォルダをコピーして、その中でビルドする。
  3. `src/extension/ashmem_memfd/ashmem_memfd.c` が `<string.h>` を読まずに `strcmp` / `memset` を使う。NDK 29 の clang は暗黙の関数宣言をエラーにする。→ `-Wno-error=implicit-function-declaration`（警告に戻す。リンク時に bionic の関数に解決される）。`-include string.h` を全体に付けると、自前で `basename()` を定義する loader が壊れる。
  4. `libandroid-shmem`（System V の共有メモリ）は使わない（任意の依存。無くてもビルドできる。`shmget` などは proot の中では動かない可能性がある。未確認）。
- **まだ確認していないこと**：実機での起動（`libproot.so` を `nativeLibraryDir` から実行して `--version`）、seccomp の設定が厳しい端末での動き、proot を APK に入れたときの `useLegacyPackaging` の影響（1b）。


### 15.8 段階 1b の測定：`.so` を展開する方式のコスト（`proot-package.yml`、2026-10-26）

実行ファイルは、ディスク上の実ファイルからしか起動できない。そのため proot を入れるには `useLegacyPackaging = true`（`android:extractNativeLibs`）が要り、アプリの**すべての** `.so` が、APK の中で圧縮され、インストール時に端末へ展開される。`proot-package.yml`（手動。何もビルドせず、実際のリリース 2 つを使う）で測った。

| 項目 | 今（`.so` を無圧縮で APK に置く） | 展開する方式 |
|---|---|---|
| APK のサイズ（ダウンロード） | 131.4 MB | **68.0 MB**（約半分） |
| 端末内の合計（APK ＋ 展開した arm64 の `.so`） | 約 131 MB | 約 117 MB（68.0 ＋ 48.8）。x86_64 と armeabi-v7a の分は圧縮のまま APK の中にあるだけで、展開されない |
| 差分更新のパッチ（0.8.17 → 0.8.18、UI の変更） | 1.1 MB | 5.9 MB（約 5 倍。圧縮された `libapp.so`（7.5 MB）の中の変更が、圧縮の流れ全体に広がるため。それでも全体の 68 MB の約 9% で、全体より十分に小さい） |
| 0.8.18 → 0.8.19（コードの変更なし） | 10 KB | 3 KB |

- arm64 の `.so` の内訳：`liblitertlm_jni.so` 20.8 MB、`libflutter.so` 11.2 MB、`libapp.so` 7.5 MB、`libarce_llama.so` 6.6 MB、`libsqlite3.so` 1.7 MB、`libomp.so` 0.9 MB。proot は約 0.3 MB を足す。
- 結論：**展開する方式にしても、ダウンロードも端末内の合計も、今より小さくなる**。代わりに、差分更新のパッチが大きくなる（それでも全体より小さい）。**未確認**：端末での起動時間の変化（インストール時に展開するので、起動のたびの展開はない）、更新のインストールにかかる時間の変化。
- 統合の方法（利用者の提案）：Android のビルドで、アプリのビルドの前に proot をビルドして（`.github/actions/proot`。サブモジュールの commit でキャッシュ）、できた `libproot.so` と `libproot_loader.so` を `android/app/src/main/jniLibs/arm64-v8a/` へ直接コピーし、`useLegacyPackaging` を有効にする。proot の成果物を別の場所に置いてあとで取りに行く形にはしない。

### 15.9 段階 1b の実装：proot をアプリに入れる（0.9.1）

- **入れ方**（利用者の案「ビルドのあとにソースを直接コピーしてリンクする」のとおり）：`release-android.yml` の `android` ジョブが、ローカルアクション `.github/actions/proot`（15.7）で proot をビルドし（サブモジュールのコミットでキャッシュ）、`libproot.so` と `libproot_loader.so` を `android/app/src/main/jniLibs/arm64-v8a/` にコピーしてから `flutter build apk` を行う。`jniLibs/` は `.gitignore` に入れてあり、リポジトリには入らない（ローカルのビルドでは入らず、アプリは「proot なし」と表示する）。x64 の APK（エミュレータ向け）には入らない。

- **まだ確認していないこと**：上のボタンの結果（実機）。

### 15.10 段階 2・3 の実装：rootfs と `run_command`（0.12.0・0.12.1）

- **構成**：モデル → `run_command`（`McpCall` として扱う）→ `McpTools._runShell` → `LinuxEnvironment`（`lib/services/linux_env.dart`）→ `MethodChannel('ai.arce.app/system')` の `linuxRun` → `SystemBridge` → `LinuxEnv.run`（Kotlin）。メインスレッドでは実行しない。
- **rootfs**：`linuxInstall` が、ダウンロード済みの tar.gz のパス・SHA-256・DNS を受け取り、`TarGz` で `linux/rootfs.partial` に展開し、`finish`（resolv.conf・hosts・hostname・apt.conf.d/99arce・workspace・tmp）をしてから `linux/rootfs` に rename する。全部成功するまで、`linux/rootfs` には触らない。
- **展開の上限**：`linuxInstall` の `maxBytes` は **0 で無制限**（Dart が 0 を渡す。Kotlin の `TarGz` は 0 以下を無制限と読む）。
- **状態**：`LinuxEnvironment` は `ChangeNotifier`。未導入／ダウンロード中（割合）／展開中／使える／失敗。設定画面の `ListenableBuilder` がこれを見る（0.12.1）。
- **容量**：`DiskUsage` が 4 KiB ブロック単位で測り、コマンドの実行中 2 秒ごとに、上限を超えかつ実行前より増えていたら止める（`killedBy = workspace`）。
- **1 つずつ**：`LinuxEnv.run` は `synchronized`。複数のチャットが同時に頼むと順番待ち。
- **設定（0.12.1）**：`shellEnabled`（道具を出すか）、`shellConfirm`（承認の要否。**チャットからは変えられない**）、`shellTimeoutSeconds`（120）、`shellMaxTimeoutSeconds`（600）、`shellMaxOutputChars`（20000）、`workspaceLimitMb`（**2048**）、`linuxRootfsUrl`・`linuxRootfsSha256`（**チャットからは変えられない**）、`linuxDns`（`1.1.1.1 8.8.8.8`）、`shellCompatMode`。`AppController._shellSettings` が毎回読み、`McpTools` の `ShellSettings` として渡す（道具の説明にも、上限とフォルダを書く）。
- **設定画面（0.12.1）**：「Linux 環境」のグループ（Android だけ）。6 つの設定の行（スイッチ・秒数・文字数・容量）、「入れる」「削除」「空にする」（確認ダイアログ）、ワークスペースの使用量（`123 MB / 2048 MB`）、`ProotCheckRow`。
- **同じ環境を共有**：チャットの道具と設定画面は、`McpTools.shellEnvironment`（1 つの `LinuxEnvironment`）を使う。`AppController.linux` がこれで、`AppController.create(linux: …)` でテスト用の偽物に差し替えられる。

### 16.2 初期の設計レビュー（2026-09-26。Kotlin 版の企画書 v1〜v3 と ARCEv2 まで）

利用者の企画書（`ARCE.AI企画書.txt` の前の版）に対して行った技術レビューの要点。決定事項は 2 章と各章に反映済み。

- **配布方法**：GitHub 配布（Play Store には出さない）に決まり、端末上でのビルドの道が開けた。Play Store の自動更新が無いので、GitHub Releases の API で新しい版を確認し、署名鍵を管理する更新機能が要る（11 章）。Android の開発者確認制度（Google が 2026 年から段階的に導入。Play Store 以外の配布も、確認済みの開発者の署名が要る）は、日本で配るときまでに登録が要る可能性がある。
- **サンドボックスの限界**：Android の権限はアプリ単位なので、同じアプリの中で動かしたコード（Chaquopy の Python、Termux 環境）は、モデル・履歴 DB・トークンを読み書きできる。本当に隔離できるのは `android:isolatedProcess="true"` の Service（承諾したファイルだけを `ParcelFileDescriptor` で渡す方式）か、別 APK（別 UID）だけ。「完全サンドボックス」ではなく、段階を分けて定義する（Artifact は WebView で強く隔離、生成コードは別プロセス＋専用の作業フォルダ＋実行前に承認で中程度）。WebView の機能を広げるときも `addJavascriptInterface` ではなく `WebViewCompat.addWebMessageListener` で、許可した origin と操作を 1 つずつ決める。**0.12.0 の `run_command` も、この意味でのサンドボックスではない**（proot はパスを変えるだけ。15.4）。
- **Termux を使わない道**：決定は「Termux 関連は実装しない」。Termux のパッケージは `/data/data/com.termux/files/usr` を前提にビルドされているので、別アプリでは動かない（自前のビルドが要る）。Termux のアプリ本体のコードは GPLv3。代わりの方法として、APK に `lib*.so` として同梱したプログラムは Android 10 以降も実行できるので、ECJ（Java のコンパイラ）→ D8 → aapt2（native 同梱）→ apksig（署名）を、アプリ内で順に呼ぶ独自のビルドを考えた（Gradle は使わない）。Python は Chaquopy（pip のパッケージはアプリのビルド時にしか入れられない）。EXE の生成は対象外（ソースコードの生成まで）。**0.12.0 の proot は、Termux のアプリを使わず、fork のソースを CI でビルドして入れる形なので、この決定に沿う**。
- **JSON の方針**：「全出力を JSON に縛る」と、回答の質が下がる（「Let Me Speak Freely?」の報告）、Qwen3 の ` thinking` と衝突する、ストリーミング表示が難しくなる、Artifact を JSON の文字列に入れるとエスケープで小さいモデルほど品質が落ちる。→ 文法は構造が必要な部分だけ（lazy grammar）、本文は Markdown、Artifact は「JSON のメタ情報＋ code fence の本体」。
- **Search**：複数方式を併用するなら、順番を決める（Raspberry Pi 5 の SearXNG → 別の検索 API → ローカルだけで続ける）。結果の重複をまとめる。
- **Agent の自動選択**：選択自体が推論になり、1.7B クラスは間違えやすい。→ ルールで絞り、迷うときだけ AI。手動変更はいつでも可能。最低モデルサイズを満たさないときはユーザーに確認する。
- **Force Execution**：メモリ不足で強制実行すると、LMK（Low Memory Killer）が捕まえられないまま終了させる。生成の状態を先に保存し、次の起動で「前回は強制実行中に終了した」と出せるようにする。
- **NPU**：LiteRT は GGUF を読めない。NPU 経路には `.litertlm` と LiteRT-LM が要る（モデル一覧は別）。実装は最初は後回し、対応端末と対応モデルを確認してから。
- **端末のテスト**：GPU の系統（Adreno と Mali）の両方で機能テストを行う。
- **開発順序**：一番難しい部分（端末上のビルド、推論のストリーミング）を先に小さく試作して確かめる。Phase 0 の試作（llama.cpp → Qwen3 → ストリーミング → Thinking → JSON / GBNF → チャット UI）は、`:core` のテスト 35 件、llama.cpp と JNI のコンパイル、生成した GBNF が llama.cpp の文法パーサーで読めること（56 ルール）まで確認した。
- **アップデート機能の仕様**：定期確認（WorkManager、最短 15 分は Android の制限）、GitHub API の最新リリース、版の比較、通知、承認後のダウンロード（Wi-Fi のみの設定、続きから再開）、SHA-256 の照合、`PackageInstaller` の Session API、同じ署名鍵でないと拒否される（鍵のバックアップ）。非公開リポジトリは access token が要り、Android Keystore で暗号化して保存する。初回だけ「提供元不明のアプリ」の許可が要る。
- **その他の指摘**：同じ設定が 2 つの画面にあった（強制実行・エラー再試行回数）→ Developer Settings だけに置く。HyperLoad と Full Performance は別機能として分けず、性能優先モードとして統合する。Qwen3 2507 版の注意と 16KB ページサイズ対応（5 章に反映）。PDF で日本語が表示されない不具合（企画書 v2 修正版）。
