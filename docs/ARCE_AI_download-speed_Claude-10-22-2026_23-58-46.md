# ARCE.AI ダウンロードの速度（0.8.8〜0.8.16）

## 1. 起きたこと
Android で、ブラウザなら 100 Mbps 出る回線で、アプリのダウンロードが 1 Mbps ほどしか出ない。アプリの更新も、モデルのダウンロードも同じ。

## 2. 原因について
- 更新もモデルも、**1 本の接続**で最初から最後まで取っていた（`lib/services/update_service.dart`、`lib/services/model_downloader.dart`）。
- 進捗の更新は間引いてあり、ハッシュ（SHA-256）の計算は 93 MB/s（サンドボックスの x86 での計測。スマホでは未計測）で、端末の処理が詰まる作りではない。
- 両方が遅いので、アプリの 1 本の接続そのものが遅いと考えられる。1 本の TCP は、パケットが落ちる回線や往復が長い回線で大きく遅くなる（輸送量はパケット損失率の平方根に反比例するという Mathis の式が知られている）。ブラウザは別の仕組み（HTTP/3 など）で通信する。
- **本当の原因が何かは、端末で測れていない**。以下は、この仮説に対する対策で、効かない場合もある。

## 3. 0.8.8 の変更：複数の接続に分けて取る
- ファイルを同じ大きさの部分に分け、**部分ごとに別の接続**で `Range` 要求を出して同時に取る（`lib/services/segmented_download.dart`）。各部分は自分のファイル（`<名前>.part.seg<番号>of<個数>`）に書き、最後に順に連結する。
- 同時接続数は設定「ダウンロードの同時接続数」（既定 4、1〜16、1 で従来どおり）。チャットの `update_settings` からも変えられる（`downloadConnections`）。1 部分は 4 MB 以上にするので、小さいファイルは分けない。
- 中断しても、部分ごとに取れた分は残り、次は続きから取る。分け方（接続数）を変えた後は、前の部分ファイルは使わず捨てる。
- サーバーが `Range` を無視して全体を返すときは、部分ファイルを消して、従来の 1 本の経路に戻る。1 本で取りかけの `.part` が残っているときも、その続きを 1 本で取る。
- 更新の取得：GitHub の API の転送先（署名付き）を、部分ごとに辿る。
- 設定の「ダウンロードの無通信の判定」は、更新だけでなくモデルのダウンロードにも使う（名前を直した）。
- 停止（一時停止）・破棄・削除のときは、部分ファイルも扱う。画面の「取得済みのバイト数」にも数える。

## 4. 確認したこと／していないこと
- 確認（テスト 422 件）：範囲の割り当てに隙間・重なりがないこと、同時に 3 本つながること、連結の中身が元と同じこと、Range 非対応のときの戻り方、切れた後に取れた分を取り直さないこと、接続数を変えたときの扱い、停止で部分を残すこと、多めに送るサーバーでも隣にはみ出さないこと、更新の取得が 2 本に分かれて同じ中身になること。
- **未確認**：実機で速くなるか。実際の GitHub と Hugging Face の保管先が、複数の Range 要求を受けるか（受けない場合は 1 本に戻る）。サーバー側が接続ごとではなく IP ごとに速度を制限している場合は、効かない。
- 速くならなければ、接続数を変えて試し、その結果（Wi-Fi かモバイル回線か、接続数ごとの速度）を教えてほしい。次の候補は、Android で Chromium の通信（HTTP/3 を含む）を使う `cronet_http`。

## 5. 0.8.13：モデルのダウンロードが止まる・エラーが読めない問題
v0.8.8 以降の実機で、モデルのダウンロードが 2 つの形で止まった：
- **`HttpException: HTTP 416`**（Qwen3-8B）：途中のファイル（`.part`）がすでにモデルと同じ大きさのとき（複数接続で取り終えて、チェックの前にアプリが止まった場合など）、「続きから」の範囲要求が 416 で断られていた。→ 同じ大きさなら再取得せずチェックに進む。長ければ捨てて最初から。416 が返ったときも、途中のファイルを捨ててもう一度最初から取る。
- **`ClientException: Connection closed while receiving data`**（Qwen3-1.7B）：サーバーが接続を閉じると、その場で止まって、手で「再開」を押す必要があった。→ モデルのダウンロードも、更新と同じく**自動で続きから取り直す**（設定「ダウンロードの試行回数」、既定 3 回。名前から「更新」を外した）。取り直すのは、通信の失敗と、サーバーが忙しいとき（HTTP 5xx・429）だけ。404 や 403 は取り直さない。一時停止は取り直さない。
- エラーの文に、CDN の**署名付き URL（数百文字）**がそのまま出ていた。→ URL を消し、「通信が途切れました（サーバーが接続を閉じました）。「再開」で続きから取ります」のような短い文にした。
- モデルの SHA-256 の計算（数 GB）を、画面と同じスレッドから**別の isolate**に移した（確認中に画面が固まらない）。
- 確認：完成済みの部分ファイル、長すぎる部分ファイル、416、途中で切れて続きから取り直す、最後まで失敗したとき、停止、取り直す対象の判定、エラー文からの URL の除去（テスト 449 件）。
- 未確認：実機で、取り直しが続いて最後まで届くか。複数接続のときに CDN が接続を閉じる原因（接続数が多すぎるのか）は、まだ分からない。閉じられやすいときは、「ダウンロードの同時接続数」を 2〜4 に下げて試してほしい。

## 6. 0.8.14：アプリを閉じているあいだもダウンロードを続ける
**分かったこと**：返信の生成と、アプリの更新のダウンロードは、Android の前面サービス（通知つきで、システムにプロセスを止められにくくする）に載っていたが、**モデルのダウンロードは載っていなかった**。他のアプリを開くと、プロセスが止められて、ダウンロードが止まっていた。

**変更**
- モデルのダウンロードを、前面サービスに載せた（通知「モデルをダウンロード中」、他のアプリを開いても続く）。ダウンロードが全部終わる・止まると、サービスも止まる。
- **アプリを閉じて（最近使ったアプリから消して）止まったダウンロード**は、次に起動したときに、取れた分から**自動で続ける**（設定「止まったダウンロードを次の起動で続ける」、既定オン。モバイル回線でも始まる）。ダウンロード中は、モデルの隣に目印のファイル（`<モデル名>.running`）を置き、終わる・一時停止すると消す。目印が残っていれば、閉じて止まったもの。自分で一時停止したものは、続けない。
- 起動したときに、途中までのファイル（1 本のものも、複数接続のものも）がある未完成のモデルを、「再開」の状態で出す（これまでは「ダウンロード」と出て、取れた分が見えなかった）。

**まだできないこと（正直に）**：最近使ったアプリから**消した瞬間**に、Android は画面と Flutter のエンジン（Dart のコード）を壊す。前面サービスはプロセスを残すが、ダウンロードをしている Dart のコードは止まる。そのため、消している間はダウンロードが進まず、次の起動で続きから取る（上の自動再開）。消している間も進めるには、ダウンロードを Kotlin のサービスの中で行う（または Flutter のエンジンをサービスが持ち続ける）必要がある。実機で試せない今の環境では、起動できなくなる危険があるので、まだ入れていない。
- 確認：途中のファイルと複数接続の部分ファイルが「再開」で出ること、目印から中断を見分けること、完成済み・何もないモデルは触らないこと、通知の種類の名前（テスト）。
- 未確認：実機で、他のアプリを開いてもモデルのダウンロードが進み続けるか。

## 7. 0.8.15：ダウンロードの部品を 1 つにまとめた
**指摘のとおり、別々だった**：モデルのダウンロード（`ModelDownloader`）とアプリの更新（`UpdateService`）が、それぞれ「複数接続・続きから取る・範囲要求・416 の扱い・取り直し・失敗の判定・エラーの文・SHA-256」を自分で持っていて、同じ直しを 2 回書いていた（0.8.13 のモデル側の直しが、更新には入っていなかった）。

**まとめたもの**
- `lib/services/file_downloader.dart`（`FileDownloader`）：1 つのファイルを、範囲要求に答える取得元から、大きければ複数接続で、途中のファイルから続きを、失敗したら自動で取り直して埋める。完成済み・長すぎる部分ファイル・サーバーが範囲を無視（200）・416 のときの扱い、無通信の判定、最後まで届かなかったときの検出、別 isolate での SHA-256 もここ。
- `lib/services/download_errors.dart`：`CancelToken`、`DownloadCancelled`、取り直す失敗の判定（`DownloadErrors.isTransient`）、画面に出す文（`DownloadErrors.explain`。署名付き URL を消す）。
- `lib/services/segmented_download.dart`：複数接続の部分取得（以前のまま。`FileDownloader` が呼ぶ）。
- モデル側（`ModelDownloader`）に残るのは、Hugging Face のどこにあるか・大きさと SHA-256 を聞くこと・チェックして置くこと。更新側（`UpdateService`）に残るのは、GitHub の API からの転送先（署名付き）の辿り方・`.sha256` の確認・差分更新・インストール。差分更新のパッチの取得も、同じ部品で取る。
- 更新側の変化：転送先が 5xx / 429 のときも取り直す（以前は取り直さなかった）。途中のファイルが範囲を断られる（416）ときも、最初から取り直す。SHA-256 は、取り終えてから別 isolate で計算する（以前は 1 つのスレッドで 1 チャンクずつ）。
- 別のまま：HTTP クライアント（`http.Client`）は、モデルの取得・更新・検索・天気がそれぞれ持っている。接続の使い回しを統一するほどの差は、今のところ無いので、そのまま。
- 確認：モデル側と更新側の既存のテスト（途中で切れて続きから、Range を無視する転送先、壊れた途中ファイル、複数接続、差分更新など）が、変えずにすべて通る（454 件）。
- 未確認：実機での動き。

## 8. 0.8.16：Windows のビルドが 0.8.8 から赤かった
**起きていたこと**：5 つの OS のリリースは、バージョンを上げた push のたびに全部始まっていた。しかし **Windows は 0.8.8 から 0.8.15 まで、テストで落ちて、リリースが出ていなかった**（最後の Windows のリリースは 0.8.7）。Android だけを見て、ほかの OS の結果を確かめていなかった。

**原因**（Windows のログで確認）：0.8.8 以降に足したテスト 4 件が、Windows で落ちた。
- 複数接続の部分ファイルを、**パスの文字列の前方一致**で探していた。Windows では同じフォルダが `/` でも `\` でも書けて、listing の結果と作ったときのパスが同じ文字列にならない。→ ファイルの**名前**で見分けるようにした（本体のコードの直し）。
- テストが、パスを `/` で割って名前を取っていた。→ `uri.pathSegments` にした。

**これから**：`AGENTS.md` に、バージョンを上げて push したら、**5 つの OS すべての結果を読む**こと、赤い OS は次のパッチで先に直すことを書いた。
- 未確認：直した Windows のビルドが通るか（push 後に確認する）。
